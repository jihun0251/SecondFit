# 05. 쿼리와 성능 — Repository, Specification, N+1

> Repository는 인터페이스만 있는데 어떻게 동작하는지, 검색 필터 6개를 어떻게 조립했는지, 그리고 JPA에서 가장 유명한 함정인 N+1 문제를 다룹니다.

---

## 1. 구현체 없는 Repository의 정체

```java
// products/repository/ProductRepository.java
public interface ProductRepository extends JpaRepository<Product, Long>, JpaSpecificationExecutor<Product> {

    Page<Product> findBySellerId(Long sellerId, Pageable pageable);
    Page<Product> findBySellerIdAndStatus(Long sellerId, Product.Status status, Pageable pageable);
    List<Product> findTop20BySellerIdAndStatusAndSuspendedFalseOrderByCreatedAtDesc(Long sellerId, Product.Status status);
}
```

**`implements`가 없습니다.** 메서드 본문도 없고요. 그런데 동작합니다.

### 어떻게?

Spring Data JPA가 애플리케이션 시작 시점에 이 인터페이스를 스캔해서 **구현 클래스를 동적으로 만들어 스프링 빈으로 등록**합니다. 우리가 `@Autowired`로 주입받는 건 그 자동 생성된 객체입니다.

```
애플리케이션 시작
  → @EnableJpaRepositories(스프링 부트가 자동 설정)가 인터페이스 스캔
  → 메서드 이름을 파싱해서 JPQL 생성
  → 프록시 구현체 생성 → 빈 등록
```

### 메서드 이름 규칙

Spring Data는 메서드 이름을 **문법처럼 읽습니다.**

```
findTop20BySellerIdAndStatusAndSuspendedFalseOrderByCreatedAtDesc
└─┬─┘└─┬─┘└──────────────┬──────────────────┘└────────┬────────┘
  │    │                 │                            │
 동작  제한          조건(WHERE)                   정렬(ORDER BY)
```

이게 이런 JPQL로 변환됩니다.

```sql
SELECT p FROM Product p
WHERE p.seller.id = ?1 AND p.status = ?2 AND p.suspended = false
ORDER BY p.createdAt DESC
LIMIT 20
```

주요 키워드:

| 키워드 | 예시 | 의미 |
|---|---|---|
| `findBy` / `existsBy` / `countBy` / `deleteBy` | | 동작 |
| `And` / `Or` | `findByTitleAndPrice` | 조건 결합 |
| `In` | `findByCategoryIdIn` | `IN (...)` |
| `True` / `False` | `SuspendedFalse` | boolean 비교 |
| `GreaterThanEqual` / `LessThan` | `findByPriceGreaterThanEqual` | 비교 |
| `Containing` / `StartingWith` | `findByTitleContaining` | LIKE |
| `Top20` / `First` | `findTop20By` | LIMIT |
| `OrderBy...Asc/Desc` | `OrderByCreatedAtDesc` | 정렬 |

> ⚠️ **오타가 나면 애플리케이션이 안 뜹니다.** `findBySellorId`라고 쓰면 시작할 때 "Sellor라는 속성이 없다"는 에러가 납니다. **런타임이 아니라 부팅 시점에 잡히는 게 장점**입니다.

### 이름이 너무 길어지면 — `@Query`

```java
// orders/repository/OrderRepository.java
@Query("SELECT COUNT(o) FROM Order o WHERE o.product.seller.id = :sellerId AND o.status = :status")
long countBySellerIdAndStatus(@Param("sellerId") Long sellerId, @Param("status") Order.Status status);
```

`orders` 테이블에는 `seller_id` 컬럼이 없습니다. 판매자를 알려면 `product`를 거쳐야 하죠. 이런 건 메서드 이름으로 표현하기 어려워서 JPQL을 직접 씁니다.

**JPQL은 SQL과 비슷하지만 테이블이 아니라 엔티티를 대상으로** 합니다.

```sql
-- SQL (테이블·컬럼)
SELECT COUNT(*) FROM orders o JOIN products p ON o.product_id = p.id WHERE p.seller_id = ?

-- JPQL (엔티티·필드)
SELECT COUNT(o) FROM Order o WHERE o.product.seller.id = :sellerId
```

JPQL에서 `o.product.seller.id`처럼 점으로 타고 들어가면 Hibernate가 알아서 조인을 만들어 줍니다.

## 2. 동적 검색 — Specification

### 문제 상황

상품 검색에는 선택 필터가 6개입니다. 사용자가 어떤 조합으로 보낼지 모릅니다.

```
GET /products?keyword=데님                      → 키워드만
GET /products?categoryId=1&size=M               → 카테고리 + 사이즈
GET /products?minPrice=10000&maxPrice=50000     → 가격대만
```

메서드 이름 방식으로는 **조합의 수만큼 메서드를 만들어야** 합니다. 6개 필터면 2⁶ = 64개죠. 불가능합니다.

### 방법 A — JPQL에 null 검사 도배 (안 씀)

```sql
SELECT p FROM Product p
WHERE p.status = :status
  AND (:keyword IS NULL OR p.title LIKE CONCAT('%', :keyword, '%'))
  AND (:categoryId IS NULL OR p.category.id = :categoryId)
  AND (:minPrice IS NULL OR p.price >= :minPrice)
  AND (:maxPrice IS NULL OR p.price <= :maxPrice)
  AND (:size IS NULL OR p.size = :size)
  AND (:conditionGrade IS NULL OR p.conditionGrade = :conditionGrade)
```

동작은 합니다만:
- 읽기 어렵습니다
- **모든 조건이 SQL에 들어가서** 인덱스를 제대로 못 탈 수 있습니다
- enum 파라미터에 `IS NULL` 비교를 하면 하이버네이트가 타입을 못 정해 에러가 나기도 합니다

### 방법 B — Specification (우리 선택)

**Specification은 "WHERE 절 조각"을 자바 객체로 만든 것**입니다.

```java
// products/repository/ProductSpecification.java
public static Specification<Product> search(ProductSearchCondition cond, List<Long> categoryIds) {
    return (root, query, cb) -> {
        List<Predicate> predicates = new ArrayList<>();

        // 항상 붙는 조건
        predicates.add(cb.equal(root.get("status"), Product.Status.ON_SALE));
        predicates.add(cb.isFalse(root.get("suspended")));

        // 값이 들어온 것만 추가
        if (StringUtils.hasText(cond.getKeyword())) {
            predicates.add(cb.like(root.get("title"), "%" + cond.getKeyword().trim() + "%"));
        }
        if (categoryIds != null && !categoryIds.isEmpty()) {
            predicates.add(root.get("category").get("id").in(categoryIds));
        }
        if (cond.getMinPrice() != null) {
            predicates.add(cb.greaterThanOrEqualTo(root.get("price"), cond.getMinPrice()));
        }
        ...
        return cb.and(predicates.toArray(new Predicate[0]));
    };
}
```

**들어온 필터만 리스트에 담고 마지막에 AND로 묶습니다.** 안 들어온 조건은 SQL에 아예 안 나타납니다.

| 이름 | 뜻 |
|---|---|
| `root` | 쿼리의 시작점 (`FROM Product p`의 `p`) |
| `cb` (CriteriaBuilder) | 조건을 만드는 도구 (`equal`, `like`, `and`...) |
| `Predicate` | 조건 하나 (`price >= 10000`) |

사용은 이렇게 합니다.

```java
// products/service/ProductService.java
Page<Product> page = productRepository.findAll(
        ProductSpecification.search(condition, resolveCategoryIds(condition.getCategoryId())),
        pageable);
```

`findAll(Specification, Pageable)`은 `JpaSpecificationExecutor`를 상속해서 생긴 메서드입니다.

### 오늘 이 부분에서 버그가 났습니다

처음엔 이렇게 썼습니다.

```java
// ❌ 처음 버전
predicates.add(cb.equal(root.get("category").get("id"), cond.getCategoryId()));
```

**정확히 일치하는 것만** 찾습니다. 그런데 상품은 소분류('니트')에 붙어 있고 사용자는 대분류('상의')로 거릅니다. `category_id = 상의ID`인 상품이 하나도 없으니 결과가 항상 비었죠.

```java
// ✅ 수정 후
if (categoryIds != null && !categoryIds.isEmpty()) {
    predicates.add(root.get("category").get("id").in(categoryIds));
}
```

```java
// products/service/ProductService.java
private List<Long> resolveCategoryIds(Long categoryId) {
    if (categoryId == null) return List.of();

    Category category = categoryRepository.findById(categoryId)
            .orElseThrow(() -> new BusinessException(ErrorCode.CATEGORY_NOT_FOUND));

    List<Long> ids = new ArrayList<>();
    ids.add(category.getId());
    category.getChildren().forEach(child -> ids.add(child.getId()));   // 하위 카테고리도
    return ids;
}
```

> 📌 **교훈**: 데이터가 계층 구조인데 조회를 평면적으로 하면 이런 구멍이 생깁니다. "상품은 어느 레벨의 카테고리에 붙는가?"를 처음에 명확히 정했어야 했습니다.

## 3. 페이징

```java
Pageable pageable = PageRequest.of(
        Math.max(condition.getPage(), 0),          // 페이지 번호 (0부터)
        normalizeSize(condition.getPageSize()),     // 페이지 크기
        toSort(condition.getSort())                 // 정렬
);
```

`Pageable`을 넘기면 Hibernate가 `LIMIT`과 `OFFSET`을 붙이고, **전체 개수를 세는 COUNT 쿼리도 자동으로** 실행합니다.

```sql
SELECT ... FROM products WHERE ... ORDER BY created_at DESC LIMIT 20 OFFSET 0;
SELECT COUNT(*) FROM products WHERE ...;   -- totalElements 계산용
```

### 페이지 크기 상한을 둔 이유

```java
private static final int MAX_PAGE_SIZE = 100;

private int normalizeSize(int size) {
    if (size <= 0) return DEFAULT_PAGE_SIZE;
    return Math.min(size, MAX_PAGE_SIZE);
}
```

이게 없으면 누군가 `?pageSize=999999`를 보내서 **DB에 있는 상품 전체를 한 번에 조회**하게 만들 수 있습니다. 메모리가 터지고 서버가 멈춥니다. 이런 걸 막는 게 방어적 프로그래밍입니다.

### 정렬을 문자열로 받는 이유

```java
private Sort toSort(String sort) {
    if (sort == null) return Sort.by(Sort.Direction.DESC, "createdAt");
    return switch (sort) {
        case "price_asc"  -> Sort.by(Sort.Direction.ASC, "price");
        case "price_desc" -> Sort.by(Sort.Direction.DESC, "price");
        default           -> Sort.by(Sort.Direction.DESC, "createdAt");
    };
}
```

`?sort=createdAt,desc` 같은 걸 그대로 받아서 `Sort`로 만들면 편하지만, **사용자가 아무 필드명이나 넣을 수 있게 됩니다.** 존재하지 않는 필드면 500이 나고, 인덱스 없는 필드로 정렬하면 성능이 무너집니다.

우리는 **허용된 값만 화이트리스트로 받고, 나머지는 기본값**으로 떨어뜨립니다.

## 4. N+1 문제 — JPA에서 가장 유명한 함정

### 문제

상품 목록 20건을 조회한다고 합시다. 각 상품의 대표 이미지를 보여줘야 하죠.

```java
// products/dto/ProductSummaryResponse.java
this.thumbnail = product.getThumbnailUrl();
```

```java
// products/entity/Product.java
public String getThumbnailUrl() {
    return this.images.stream()   // ⭐ LAZY 컬렉션 접근
            .filter(ProductImage::isThumbnail)
            .findFirst()
            ...
}
```

`images`는 `@OneToMany`라 LAZY입니다. 그러면 이런 일이 벌어집니다.

```sql
-- ① 상품 목록 (1번)
SELECT * FROM products WHERE status = 'ON_SALE' LIMIT 20;

-- ② 각 상품의 이미지 (20번!)
SELECT * FROM product_images WHERE product_id = 1;
SELECT * FROM product_images WHERE product_id = 2;
SELECT * FROM product_images WHERE product_id = 3;
...
SELECT * FROM product_images WHERE product_id = 20;
```

**쿼리 1개 + N개 = 총 21개.** 이게 N+1 문제입니다. 목록이 100건이면 101개가 나갑니다.

### 해결책들

**(A) fetch join** — 한 방에 조인해서 가져오기

```sql
SELECT p FROM Product p JOIN FETCH p.images WHERE ...
```

빠르지만 **페이징과 같이 쓸 수 없습니다.** 상품 1개에 이미지 3장이면 결과 행이 3줄이 되는데, `LIMIT 20`을 걸면 상품 7개만 나옵니다. Hibernate는 이 경우 경고를 남기고 **전체를 메모리에 올린 뒤 자바에서 자르는데**, 데이터가 많으면 그대로 터집니다.

**(B) `@EntityGraph`** — fetch join의 어노테이션 버전. 같은 문제가 있습니다.

**(C) batch fetch (우리 선택)**

```yaml
# backend/src/main/resources/application.yaml
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100
```

**설정 한 줄**입니다. 동작이 이렇게 바뀝니다.

```sql
-- ① 상품 목록
SELECT * FROM products WHERE status = 'ON_SALE' LIMIT 20;

-- ② 이미지를 IN 절로 한 번에
SELECT * FROM product_images WHERE product_id IN (1,2,3,...,20);
```

**21개 → 2개**가 됐습니다.

원리는 간단합니다. 첫 번째 프록시가 초기화될 때 "어차피 나머지도 곧 필요하겠네" 하고 **최대 100개씩 묶어서 IN 절로 가져옵니다.**

| 방식 | 쿼리 수 | 페이징 |
|---|---|---|
| 아무것도 안 함 | 1 + N | ✅ |
| fetch join | 1 | ❌ 위험 |
| batch fetch | 1 + (N/100) | ✅ |

> 💡 **왜 100인가?** IN 절에 너무 많은 값을 넣으면 DB가 힘들어하고, 너무 적으면 쿼리 수가 늘어납니다. 보통 100~1000 사이를 씁니다.

### 확인하는 법

`application.yaml`에 `show-sql: true`가 켜져 있습니다. 상품 목록을 한 번 조회하고 **콘솔에 SQL이 몇 개 찍히는지** 세어 보세요. `default_batch_fetch_size` 줄을 주석 처리하고 다시 해보면 차이가 확 보입니다.

## 5. 인덱스

```java
// products/entity/Product.java
@Table(
        name = "products",
        indexes = {
                @Index(name = "idx_products_seller", columnList = "seller_id"),
                @Index(name = "idx_products_category", columnList = "category_id"),
                @Index(name = "idx_products_status", columnList = "status"),
                @Index(name = "idx_products_created", columnList = "created_at")
        }
)
```

### 인덱스가 뭔가

책 뒤의 찾아보기(색인)와 같습니다. "인덱스"라는 단어를 찾을 때 책을 처음부터 넘기는 대신 색인을 보면 "372쪽"이 바로 나오죠.

인덱스가 없으면 DB는 **모든 행을 하나씩 검사**합니다(풀 테이블 스캔). 상품이 10만 건이면 10만 번 읽습니다.

### 어디에 거나

**WHERE, ORDER BY, JOIN에 자주 쓰이는 컬럼**에 겁니다.

```sql
SELECT * FROM products
WHERE status = 'ON_SALE'      -- idx_products_status
  AND category_id IN (...)    -- idx_products_category
ORDER BY created_at DESC      -- idx_products_created
LIMIT 20;
```

우리 목록 쿼리가 실제로 쓰는 컬럼들입니다.

### 공짜가 아니다

인덱스는 **별도의 자료구조(B-Tree)** 를 유지합니다. 그래서:
- INSERT/UPDATE/DELETE가 느려집니다 (인덱스도 갱신해야 하니까)
- 저장 공간을 씁니다

**읽기가 많은 컬럼에만** 걸어야 합니다. 모든 컬럼에 인덱스를 거는 건 안 거는 것만큼 나쁩니다.

### 유니크 제약도 인덱스다

```java
uniqueConstraints = {
        @UniqueConstraint(name = "uk_users_email", columnNames = "email"),
        @UniqueConstraint(name = "uk_users_nickname", columnNames = "nickname")
}
```

유니크 제약은 "중복을 막는다"는 규칙인 동시에 **인덱스이기도** 합니다. 중복을 검사하려면 빠르게 찾을 수 있어야 하니까요. 그래서 `findByEmail()`이 빠릅니다.

> ⚠️ **애플리케이션 검사만으로는 부족합니다.** `userRepository.existsByEmail()`로 검사해도, 두 요청이 **동시에** 들어오면 둘 다 "없음"을 확인하고 둘 다 INSERT할 수 있습니다. DB의 유니크 제약이 최후의 방어선입니다.

## 6. 집계 쿼리

```java
// reviews/repository/ReviewRepository.java
@Query("SELECT AVG(r.rating) FROM Review r WHERE r.seller.id = :sellerId")
Double findAverageRatingBySellerId(@Param("sellerId") Long sellerId);
```

### 반환 타입이 `Double`(래퍼)인 이유

리뷰가 **하나도 없으면** SQL의 `AVG()`는 `NULL`을 반환합니다. `double`(원시 타입)로 받으면 언박싱하다가 `NullPointerException`이 납니다.

```java
// users/service/UserService.java
private double averageRating(Long userId) {
    Double average = reviewRepository.findAverageRatingBySellerId(userId);
    return average == null ? 0.0 : Math.round(average * 10) / 10.0;
}
```

`null`을 명시적으로 처리하고, 소수점 1자리로 반올림합니다. (`4.666...` → `4.7`)

## 7. 조회수 증가는 왜 쿼리가 아닌가

```java
@Transactional
public ProductDetailResponse getDetail(Long productId) {
    Product product = productRepository.findById(productId).orElseThrow(...);
    product.increaseViewCount();   // 자바 객체의 값만 +1
    ...
}
```

이렇게 할 수도 있었습니다.

```java
@Modifying
@Query("UPDATE Product p SET p.viewCount = p.viewCount + 1 WHERE p.id = :id")
void increaseViewCount(@Param("id") Long id);
```

| | 더티 체킹 (우리 방식) | `@Modifying` 쿼리 |
|---|---|---|
| 쿼리 수 | SELECT + UPDATE | UPDATE 1개 |
| 동시성 | 두 요청이 겹치면 하나가 덮어씀 | DB가 원자적으로 처리 |
| 코드 | 자연스러움 | 영속성 컨텍스트와 불일치 위험 |

**조회수는 몇 번 틀려도 상관없는 값**이라 우리는 더티 체킹을 택했습니다. 어차피 상세 조회를 위해 SELECT는 해야 하니 추가 비용도 없고요.

하지만 **재고나 잔액이라면 얘기가 다릅니다.** 그땐 원자적 UPDATE나 비관적 락(`@Lock(PESSIMISTIC_WRITE)`)이 필요합니다.

## 8. 우리 코드에 남아 있는 성능 이슈 (솔직하게)

배우는 입장에서는 "완벽한 코드"보다 **"어디가 부족한지 아는 코드"** 가 낫습니다.

**① 관리자 신고 목록의 N+1**

```java
// reports/service/ReportService.java
return PageResponse.of(result, report -> {
    long count = report.getProduct() == null
            ? 0
            : reportRepository.countByProductId(report.getProduct().getId());   // ⭐ 건마다 쿼리
    return ReportDtos.Item.of(report, count);
});
```

신고 20건이면 COUNT 쿼리가 20번 나갑니다. `GROUP BY product_id`로 한 번에 세는 쿼리로 바꾸면 1번이 됩니다. 관리자 화면이고 건수가 적어서 일단 뒀습니다.

**② 검색 키워드에 앞 와일드카드**

```java
cb.like(root.get("title"), "%" + keyword + "%")
```

`LIKE '%데님%'`은 **인덱스를 못 씁니다.** 앞부분이 열려 있어서 색인으로 범위를 좁힐 수 없거든요. 상품이 많아지면 느려집니다. 제대로 하려면 MySQL Full-Text Index나 Elasticsearch가 필요합니다.

**③ 동시 주문 경합**

`Product.markPaid()`가 `ON_SALE`인지 검사하지만, 두 요청이 **거의 동시에** 들어오면 둘 다 검사를 통과할 수 있습니다. 막으려면 `@Version`(낙관적 락)이나 `SELECT ... FOR UPDATE`(비관적 락)가 필요합니다.

> 📌 발표에서 이런 걸 먼저 말하면 좋습니다. "여기까지 알고 있고, 지금 단계에서는 이렇게 판단했다"는 게 "완벽합니다"보다 훨씬 신뢰를 줍니다.

## 스스로 확인해보기

**Q1.** `ProductRepository`는 인터페이스뿐인데 어떻게 동작하나요?

**Q2.** 검색 필터가 6개일 때 메서드 이름 방식(`findByXxxAndYyy...`)을 쓸 수 없는 이유는?

**Q3.** N+1 문제가 무엇이고, `default_batch_fetch_size`가 어떻게 해결하나요?

**Q4.** fetch join으로 N+1을 해결하면 안 되는 상황은 언제인가요?

**Q5.** `findAverageRatingBySellerId()`의 반환 타입이 `double`이 아니라 `Double`인 이유는?

<details>
<summary>답 보기</summary>

**A1.** Spring Data JPA가 애플리케이션 시작 시 인터페이스를 스캔해서, 메서드 이름을 파싱하거나 `@Query`를 읽어 구현 클래스를 동적으로 생성하고 스프링 빈으로 등록합니다.

**A2.** 사용자가 어떤 필터 조합을 보낼지 모르므로 모든 경우의 수(2⁶ = 64개)에 대한 메서드가 필요해집니다. 그래서 조건을 런타임에 조립하는 Specification을 씁니다.

**A3.** 목록 N건을 조회한 뒤 각 건의 연관 데이터를 하나씩 조회하면서 쿼리가 1+N개 나가는 문제입니다. `default_batch_fetch_size`를 켜면 Hibernate가 연관 데이터를 최대 N개씩 묶어 `IN` 절 한 번으로 가져와서 1+(N/배치크기)로 줄어듭니다.

**A4.** 페이징과 함께 쓸 때입니다. 일대다 조인은 결과 행이 뻥튀기되어 `LIMIT`이 원하는 대로 동작하지 않고, Hibernate가 전체를 메모리에 올려 자바에서 자르기 때문에 데이터가 많으면 메모리가 터집니다.

**A5.** 리뷰가 하나도 없으면 SQL `AVG()`가 NULL을 반환하는데, 원시 타입 `double`로 받으면 언박싱 과정에서 NullPointerException이 발생합니다.

</details>
