# 06. 프론트엔드 연동

> 21개 페이지가 전부 목업이었던 걸 실제 API로 바꿨습니다. 페이지마다 `fetch`를 쓰지 않고 공통 모듈로 묶은 이유, 로그인 상태를 어떻게 공유하는지가 핵심입니다.

---

## 1. 연동 전에는 이랬습니다

```typescript
// 예전 SignupPage.tsx
const handleSubmit = async () => {
  try {
    const response = await fetch("http://localhost:8080/api/v1/users/signup", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ email, password, nickname, phone }),
    });
    const data = await response.json();
    if (response.ok) {
      alert("회원가입 성공!");
    } else {
      alert("실패: " + data.error.message);
    }
  } catch (error) {
    alert("서버에 연결할 수 없습니다.");
  }
};
```

이걸 21개 페이지 × 여러 API에 걸쳐 반복하면 어떻게 될까요?

- 서버 주소가 바뀌면 **전부 수정**
- 토큰 헤더를 붙이는 코드를 **매번 복사**
- `{success, data, error}` 봉투 벗기는 코드를 **매번 복사**
- 에러 처리 방식이 페이지마다 **제각각**
- 응답 타입을 몰라서 `data.어쩌구`에 오타가 나도 **런타임에야 발견**

## 2. 3층으로 나눴습니다

```
src/api/
├── types.ts     ← 백엔드 DTO와 1:1 대응하는 타입 정의
├── client.ts    ← fetch 래퍼 (토큰, 봉투, 에러)
└── index.ts     ← 도메인별 API 함수
```

### `client.ts` — 모든 통신이 지나가는 관문

```typescript
async function request<T>(path: string, options: RequestOptions = {}): Promise<T> {
  const { method = "GET", body, formData, auth = true } = options;

  const headers: Record<string, string> = {};
  const token = tokenStorage.get();

  if (auth && token) {
    headers["Authorization"] = `Bearer ${token}`;        // ① 토큰 자동 첨부
  }
  if (body !== undefined && !formData) {
    headers["Content-Type"] = "application/json";
  }

  let response: Response;
  try {
    response = await fetch(`${BASE_URL}${API_PREFIX}${path}`, { method, headers, body: ... });
  } catch {
    throw new ApiError(0, "NETWORK_ERROR", "서버에 연결할 수 없습니다...");   // ② 네트워크 오류
  }

  if (response.status === 204) {                          // ③ 본문 없는 응답
    return undefined as T;
  }

  const payload: ApiResponse<T> = await response.json();

  if (!response.ok || payload.success === false) {        // ④ 에러를 예외로
    throw new ApiError(response.status,
                       payload.error?.code ?? "UNKNOWN",
                       payload.error?.message ?? "요청 처리 중 오류가 발생했습니다.");
  }

  return payload.data as T;                               // ⑤ 봉투 벗겨서 알맹이만
}
```

이 한 함수가 다섯 가지를 처리합니다.

| | 처리 내용 |
|---|---|
| ① | 토큰이 있으면 `Authorization` 헤더 자동 추가 |
| ② | 서버가 꺼져 있을 때도 같은 형태의 에러로 변환 |
| ③ | 삭제 API의 204 No Content 처리 |
| ④ | 실패를 **예외로 던짐** → 호출부는 성공 경로만 쓰면 됨 |
| ⑤ | `{success, data}` 봉투를 벗겨 `data`만 반환 |

### ⚠️ FormData일 때 Content-Type을 넣지 않는 이유

```typescript
if (body !== undefined && !formData) {
  headers["Content-Type"] = "application/json";
}
```

파일 업로드에서 `Content-Type: multipart/form-data`를 **직접 넣으면 안 됩니다.**

multipart 요청은 각 파트를 구분하는 **boundary 문자열**이 필요합니다.

```
Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryABC123
                                   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
```

이 boundary는 브라우저가 무작위로 만들어 헤더에 넣어줍니다. 우리가 헤더를 직접 지정하면 boundary가 빠져서 **서버가 요청 본문을 파싱하지 못합니다.**

`fetch`에 `FormData`를 넘기면서 Content-Type을 **비워두면** 브라우저가 알아서 채웁니다.

### 에러를 예외로 던지는 이유

```typescript
// ❌ 반환값으로 성공/실패를 구분하면
const result = await api.createProduct(data);
if (!result.success) { ... }   // 매번 검사

// ✅ 예외로 던지면
try {
  await productApi.create(data);   // 성공 경로만 씀
  navigate("/my/sales");
} catch (e) {
  alert(e instanceof ApiError ? e.message : "...");
}
```

성공 흐름과 에러 흐름이 시각적으로 분리되어 읽기 쉬워집니다.

### `ApiError` — 코드로 분기할 수 있게

```typescript
export class ApiError extends Error {
  readonly status: number;
  readonly code: string;

  get isUnauthorized() {
    return this.status === 401;
  }
}
```

백엔드가 준 `code`(`"EMAIL_DUPLICATED"` 등)를 그대로 담습니다. 나중에 "이메일 중복이면 이메일 입력칸을 빨갛게" 같은 처리를 할 수 있습니다.

## 3. `types.ts` — 백엔드 DTO를 타입으로 옮기기

```typescript
export interface ProductDetail {
  productId: number;
  title: string;
  description: string | null;
  price: number;
  size: string | null;
  conditionGrade: ConditionGrade;
  category: { id: number; name: string } | null;
  status: ProductStatus;
  images: { imageId: number; url: string; isThumbnail: boolean }[];
  seller: { userId: number; nickname: string; rating: number | null };
}
```

### `| null`을 정확히 붙이는 게 중요합니다

백엔드에서 `description`이 `@Column`에 `nullable`이면 null이 올 수 있습니다. 타입에 `| null`을 적어두면 TypeScript가 강제합니다.

```typescript
<p>{product.description}</p>              // 그냥 쓰면 "null"이 화면에 출력될 수 있음
<p>{product.description ?? "등록된 설명이 없습니다."}</p>   // ✅
```

### enum 라벨 매핑

백엔드는 항상 영문 enum을 줍니다. 화면에는 한글이 필요하죠.

```typescript
export const PRODUCT_STATUS_LABEL: Record<ProductStatus, string> = {
  PENDING_INBOUND: "입고 대기",
  ON_SALE: "판매중",
  PAID: "결제완료",
  SHIPPED: "출고",
  DELIVERED: "배송완료",
  SETTLED: "정산완료",
};
```

`Record<ProductStatus, string>`이 핵심입니다. **enum에 새 값이 추가되면 여기에도 추가하지 않으면 컴파일 에러가 납니다.** 번역 누락을 컴파일러가 잡아줍니다.

```typescript
<span>● {PRODUCT_STATUS_LABEL[s.status]}</span>
```

> 💡 예전 목업에서는 백엔드가 `statusLabel: "판매중"` 같은 한글을 같이 내려주는 구조였습니다. 하지만 **표시 문구는 화면의 관심사**입니다. 나중에 영어 지원을 하거나 문구를 바꿀 때 백엔드를 고치는 건 이상하죠.

## 4. `index.ts` — 도메인별 API 함수

```typescript
export const productApi = {
  search: (params: ProductSearchParams = {}) =>
    http.get<Page<ProductSummary>>(`/products${toQuery(params as Record<string, unknown>)}`),

  getDetail: (productId: number) => http.get<ProductDetail>(`/products/${productId}`),

  create: (body: ProductCreateRequest) =>
    http.post<{ productId: number; status: ProductStatus }>("/products", body),

  remove: (productId: number) => http.delete<void>(`/products/${productId}`),

  aiTagging: (image: File) => {
    const form = new FormData();
    form.append("image", image);
    return http.postForm<AiTagging>("/products/ai-tagging", form);
  },
};
```

**페이지는 URL 문자열을 절대 다루지 않습니다.**

```typescript
// ❌ 페이지에서
fetch(`http://localhost:8080/api/v1/products/${id}`)

// ✅ 페이지에서
productApi.getDetail(id)
```

API 경로가 바뀌면 `index.ts` 한 곳만 고치면 됩니다. 그리고 반환 타입이 정해져 있어서 자동완성이 됩니다.

### `toQuery` — 빈 값 걸러내기

```typescript
export function toQuery(params: Record<string, unknown>): string {
  const search = new URLSearchParams();
  Object.entries(params).forEach(([key, value]) => {
    if (value === undefined || value === null || value === "") return;   // ⭐
    search.append(key, String(value));
  });
  const query = search.toString();
  return query ? `?${query}` : "";
}
```

이게 없으면 `?keyword=&categoryId=&minPrice=` 같은 빈 파라미터가 붙습니다. 백엔드가 빈 문자열을 "필터 없음"이 아니라 "빈 문자열로 검색"으로 해석할 수도 있고요.

## 5. Context — 로그인 상태 공유하기

### 문제

로그인 정보가 필요한 곳이 많습니다.
- Header: 닉네임 표시, 로그아웃 버튼
- ProductDetailPage: 내 상품인지 판단
- ProtectedRoute: 접근 차단
- OrdersPage, ProfilePage...

props로 내려주면 이렇게 됩니다.

```
App → HomePage → Header
    → ProductListPage → Header
    → ProductDetailPage → Header
```

모든 페이지가 쓰지도 않는 `user`를 받아서 Header로 넘겨야 합니다. 이걸 **props drilling**이라고 합니다.

### Context가 해결합니다

```typescript
// contexts/AuthContext.tsx
const AuthContext = createContext<AuthContextType | undefined>(undefined);

export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<AuthUser | null>(readStoredUser);

  const login = async (email: string, password: string) => {
    const result = await authApi.login(email, password);
    tokenStorage.set(result.accessToken);
    localStorage.setItem(USER_KEY, JSON.stringify(result.user));
    setUser(result.user);
    return result.user;
  };

  const logout = () => {
    authApi.logout().catch(() => undefined);
    tokenStorage.clear();
    localStorage.removeItem(USER_KEY);
    setUser(null);
  };

  return (
    <AuthContext.Provider value={{ user, isLoggedIn: user !== null, isAdmin: user?.role === "ADMIN", login, logout }}>
      {children}
    </AuthContext.Provider>
  );
}

export function useAuth() {
  const context = useContext(AuthContext);
  if (!context) {
    throw new Error("useAuth는 AuthProvider 안에서만 사용할 수 있습니다.");
  }
  return context;
}
```

Provider로 감싼 안쪽이면 **어디서든** 꺼내 쓸 수 있습니다.

```typescript
const { user, isLoggedIn, isAdmin, logout } = useAuth();
```

### 커스텀 훅으로 감싼 이유

`useContext(AuthContext)`를 직접 쓰면 Provider 밖에서 호출했을 때 `undefined`가 반환되고, `user.nickname`에서 뜬금없는 에러가 납니다.

`useAuth()`로 감싸고 안에서 검사하면 **"AuthProvider 안에서만 사용할 수 있습니다"** 라는 명확한 메시지가 나옵니다. 디버깅 시간이 확 줄어듭니다.

### `localStorage`로 새로고침 견디기

```typescript
const [user, setUser] = useState<AuthUser | null>(readStoredUser);
```

`useState`의 초기값을 **함수로** 넘기면 첫 렌더링 때 한 번만 실행됩니다(lazy initialization). `localStorage`에서 읽어오는 건 비용이 있으니 매 렌더링마다 하면 낭비죠.

새로고침하면 React 상태는 사라지지만 `localStorage`는 남아 있어서 로그인이 유지됩니다.

> ⚠️ **보안 참고**: `localStorage`는 JS로 접근 가능해서 XSS 공격에 취약합니다. 더 안전한 방식은 `httpOnly` 쿠키인데, 그러면 CSRF 대응이 필요해집니다. 어느 쪽이든 트레이드오프가 있고, 개인 프로젝트에서는 localStorage가 일반적입니다.

## 6. 찜 Context — 낙관적 업데이트

찜은 목업일 땐 그냥 배열이었습니다.

```typescript
// 예전 LikesContext.tsx
const [likedIds, setLikedIds] = useState<number[]>([1042, 1043, 1048]);
const toggleLike = (id: number) => { setLikedIds(prev => ...); };
```

이제 **서버가 진짜 주인**입니다. 그런데 그냥 이렇게 하면 문제가 있습니다.

```typescript
// ❌ 서버 응답을 기다린 뒤 화면 갱신
const toggleWish = async (productId: number) => {
  await wishlistApi.add(productId);   // 200ms 걸린다면
  await reload();                      // 또 150ms
};
// → 하트를 눌렀는데 350ms 동안 아무 반응이 없음
```

### 낙관적 업데이트(Optimistic Update)

**"어차피 성공할 테니 화면부터 바꾸고, 실패하면 되돌린다"** 는 전략입니다.

```typescript
// contexts/WishlistContext.tsx
const toggleWish = async (productId: number) => {
  if (!isLoggedIn) {
    alert("로그인이 필요합니다.");
    return;
  }

  const wished = isWished(productId);

  // ① 서버 응답을 기다리지 않고 하트부터 바꾼다
  setItems((prev) =>
    wished
      ? prev.filter((item) => item.productId !== productId)
      : [...prev, { productId, title: "", price: 0, priceChange: 0, status: "ON_SALE", thumbnail: null }]
  );

  try {
    if (wished) {
      await wishlistApi.remove(productId);
    } else {
      await wishlistApi.add(productId);
    }
    await reload();          // ② 서버 기준으로 다시 맞춘다 (가격 변동 등)
  } catch (error) {
    await reload();          // ③ 실패하면 원래 상태로 복구
    alert(error instanceof Error ? error.message : "찜 처리에 실패했습니다.");
  }
};
```

사용자는 **즉시 반응**을 봅니다. 실패는 드물고, 실패하면 되돌리면서 알려줍니다.

## 7. Provider 중첩 순서

```typescript
// App.tsx
<AuthProvider>
  <BrowserRouter>
    <WishlistProvider>
      <Routes>...</Routes>
    </WishlistProvider>
  </BrowserRouter>
</AuthProvider>
```

**순서에 이유가 있습니다.**

- `WishlistProvider`가 `useAuth()`를 씁니다(로그인 여부를 알아야 찜 목록을 불러올지 판단). 그래서 `AuthProvider`가 **바깥**에 있어야 합니다.
- `ProtectedRoute`가 `useNavigate`/`Navigate`를 쓰므로 `BrowserRouter` **안**에 있어야 합니다.

Context를 쓰는 쪽은 항상 Provider 안쪽이어야 합니다.

## 8. `useAsync` — 반복되는 3단 상태 묶기

거의 모든 페이지가 이 패턴입니다.

```typescript
// ❌ 페이지마다 반복
const [data, setData] = useState<X | null>(null);
const [loading, setLoading] = useState(true);
const [error, setError] = useState<string | null>(null);

useEffect(() => {
  (async () => {
    setLoading(true);
    try { setData(await api.fetchX()); }
    catch (e) { setError(...); }
    finally { setLoading(false); }
  })();
}, []);
```

21개 페이지에 이걸 쓰면 300줄이 넘습니다. **커스텀 훅으로 한 번만 씁니다.**

```typescript
// hooks/useAsync.ts
export function useAsync<T>(fetcher: () => Promise<T>, deps: unknown[] = []) {
  const [data, setData] = useState<T | null>(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  const memoizedFetcher = useCallback(fetcher, deps);

  const run = useCallback(async () => {
    setLoading(true);
    setError(null);
    try {
      setData(await memoizedFetcher());
    } catch (e) {
      setError(e instanceof ApiError ? e.message : "데이터를 불러오지 못했습니다.");
    } finally {
      setLoading(false);
    }
  }, [memoizedFetcher]);

  useEffect(() => { void run(); }, [run]);

  return { data, loading, error, reload: run };
}
```

사용은 한 줄입니다.

```typescript
// pages/ProductListPage.tsx
const { data, loading, error } = useAsync(
  () => productApi.search({ keyword, categoryId, size: selectedSize, sort, page: 0, pageSize: 40 }),
  [keyword, categoryId, selectedSize, selectedGrade, maxPrice, sort]   // ⭐ 이게 바뀌면 다시 호출
);
```

`deps` 배열에 넣은 값이 바뀌면 **자동으로 다시 조회**합니다. 필터를 바꾸면 알아서 서버에 다시 물어보는 거죠.

### `reload`가 필요한 이유

```typescript
// pages/admin/AdminInboundsPage.tsx
const { data, loading, error, reload } = useAsync(() => adminApi.getInbounds({ status }), [status]);

const handleConfirm = async (inboundId: number) => {
  await run(async () => {
    await adminApi.confirmInbound(inboundId);
    await reload();   // ⭐ 입고 확인 후 목록 갱신
  }, "입고 확인 완료...");
};
```

데이터를 바꿨으면 화면도 새로 받아와야 합니다.

### `useAction` — 버튼 클릭용

```typescript
export function useAction() {
  const [running, setRunning] = useState(false);

  const run = async (action: () => Promise<void>, successMessage?: string) => {
    if (running) return false;      // ⭐ 중복 클릭 차단
    setRunning(true);
    try {
      await action();
      if (successMessage) alert(successMessage);
      return true;
    } catch (e) {
      alert(e instanceof ApiError ? e.message : "요청 처리에 실패했습니다.");
      return false;
    } finally {
      setRunning(false);
    }
  };

  return { running, run };
}
```

`if (running) return false;`가 중요합니다. 사용자가 "결제하기"를 빠르게 두 번 누르면 **주문이 두 건 생길 수 있습니다.** 이걸 막습니다.

```typescript
<button className="btn-pay" onClick={handlePay} disabled={running}>
  {running ? "결제 처리 중..." : "결제하기"}
</button>
```

## 9. ProtectedRoute — 화면 접근 차단

```typescript
// components/ProtectedRoute.tsx
function ProtectedRoute({ children, adminOnly = false }: Props) {
  const { isLoggedIn, isAdmin } = useAuth();
  const location = useLocation();

  if (!isLoggedIn) {
    return <Navigate to="/login" state={{ from: location.pathname }} replace />;
  }

  if (adminOnly && !isAdmin) {
    return <div>접근 권한이 없습니다</div>;
  }

  return <>{children}</>;
}
```

```typescript
// App.tsx
<Route path="/my/orders" element={<ProtectedRoute><OrdersPage /></ProtectedRoute>} />
<Route path="/admin/inbounds" element={<ProtectedRoute adminOnly><AdminInboundsPage /></ProtectedRoute>} />
```

### 왜 백엔드가 막는데 프론트도 막나

백엔드는 **API 요청**을 401/403으로 거절합니다. 하지만 그건 "요청이 실패"하는 것이지, **화면이 안 보이는 건 아닙니다.**

프론트 가드가 없으면 비로그인 사용자가 `/my/orders`에 들어가서 → 빈 화면 + 에러 메시지를 보게 됩니다. 로그인 페이지로 보내주는 게 맞죠.

> 📌 **중요**: 프론트 가드는 **편의**지 보안이 아닙니다. 브라우저 개발자 도구로 얼마든지 우회할 수 있습니다. **진짜 방어는 항상 백엔드에서** 합니다. 프론트는 UX를 위해 한 번 더 막는 것뿐입니다.

### `state={{ from: location.pathname }}`

로그인 후 원래 가려던 곳으로 돌려보내기 위해 경로를 넘깁니다.

```typescript
// pages/LoginPage.tsx
const from = (location.state as LocationState | null)?.from;

const user = await login(email, password);
if (from) navigate(from, { replace: true });
else if (user.role === "ADMIN") navigate("/admin/inbounds", { replace: true });
else navigate("/", { replace: true });
```

`replace: true`는 브라우저 히스토리에 **덮어쓰기**입니다. 이게 없으면 로그인 후 뒤로가기를 눌렀을 때 다시 로그인 페이지가 나옵니다.

## 10. 결제 흐름 재구성 — 화면 순서와 API 순서가 달랐다

목업 화면 순서는 이랬습니다.

```
CheckoutPage(결제수단 선택) → AddressPage(배송지) → DeliveryPage(배송현황)
```

그런데 백엔드 API 순서는 이렇습니다.

```
POST /orders          (주문 생성, 상품 ON_SALE → PAID)
POST /payments        (모의 결제)
PATCH /orders/{id}/shipping   (배송지 입력)
```

**배송지가 나중입니다.** 그래서 CheckoutPage에서 주문+결제를 처리하고, AddressPage로 `orderId`를 넘겨야 했습니다.

```typescript
// pages/CheckoutPage.tsx
const handlePay = async () => {
  await run(async () => {
    const order = await orderApi.create(product.productId);
    await paymentApi.pay(order.orderId, order.orderPrice, method);

    navigate(`/checkout/${product.productId}/address`, {
      state: { orderId: order.orderId },   // ⭐ URL에는 productId만 있으므로 state로 전달
      replace: true,
    });
  });
};
```

```typescript
// pages/AddressPage.tsx
const orderId = (location.state as { orderId?: number } | null)?.orderId;

if (!orderId) {
  return <div>주문 정보가 없습니다. 상품 페이지에서 결제를 먼저 진행해 주세요.</div>;
}
```

주소창에 직접 URL을 치고 들어온 경우를 대비해 방어 코드를 넣었습니다.

### 배송비 3,000원을 없앤 이유

목업에는 "상품 89,000 + 배송비 3,000 = 92,000원"이 있었습니다. 그런데 백엔드는 이렇게 검사합니다.

```java
// payments/service/PaymentService.java
if (request.getAmount() != order.getOrderPrice()) {
    throw new BusinessException(ErrorCode.PAYMENT_AMOUNT_MISMATCH);
}
```

92,000원을 보내면 **무조건 400 에러**입니다. 배송비를 지원하려면 백엔드에 `shipping_fee` 개념이 있어야 하는데 없거든요. 그래서 화면을 "배송비 무료"로 바꿨습니다.

> 📌 **교훈**: 목업 화면을 만들 때 백엔드에 없는 개념을 그리면 나중에 반드시 충돌합니다. 화면과 API 스펙을 같이 설계해야 하는 이유입니다.

## 11. 파일 업로드 — 순환 참조를 푼 이야기

상품 등록 API는 이미지 **URL 배열**을 요구합니다.

```json
{ "images": ["https://.../1.jpg", "https://.../2.jpg"] }
```

그런데 파일 업로드 API는 **이미 존재하는 상품**을 요구합니다.

```
POST /products/{productId}/images
```

**등록하려면 URL이 필요하고, URL을 얻으려면 상품이 있어야 합니다.** 순환입니다.

### 해결 — 상품과 무관한 업로드 엔드포인트 추가

```java
// backend: products/controller/ProductController.java
@PostMapping(value = "/images/upload", consumes = "multipart/form-data")
public ResponseEntity<ApiResponse<Map<String, String>>> uploadImage(@RequestPart("file") MultipartFile file) {
    return ResponseEntity.status(HttpStatus.CREATED)
            .body(ApiResponse.success(Map.of("url", productService.uploadImage(file))));
}
```

```typescript
// frontend: pages/ProductCreatePage.tsx
const handleSubmit = async () => {
  await run(async () => {
    // 1) 파일을 먼저 올려 URL을 확보
    const uploaded = await Promise.all(
      images.map((image) => productApi.uploadImageFile(image.file))
    );

    // 2) 확보한 URL로 상품 등록
    await productApi.create({
      categoryId, title, price: Number(price), conditionGrade: grade,
      images: uploaded.map((u) => u.url),
      thumbnailIndex: 0,
      aiSuggestedCategory: aiResult?.category ?? undefined,
      ...
    });
  });
};
```

`Promise.all`은 여러 업로드를 **동시에** 실행합니다. 순차적으로 하면 8장 × 200ms = 1.6초인데, 동시에 하면 200ms입니다.

### 미리보기 — `URL.createObjectURL`

```typescript
const next = picked.map((file) => ({
  file,
  previewUrl: URL.createObjectURL(file),   // 브라우저 메모리의 파일을 가리키는 임시 URL
}));
```

업로드하기 전에 화면에 보여주려면 이게 필요합니다. `blob:http://localhost:5173/abc-123` 같은 URL이 만들어집니다.

```typescript
const removeImage = (index: number) => {
  URL.revokeObjectURL(images[index].previewUrl);   // ⭐ 메모리 해제
  setImages(images.filter((_, i) => i !== index));
};
```

`revokeObjectURL`을 안 부르면 브라우저가 파일을 계속 메모리에 들고 있습니다(메모리 누수).

## 12. AI 태깅 연동

```typescript
// pages/ProductCreatePage.tsx
const handlePickFiles = (event: React.ChangeEvent<HTMLInputElement>) => {
  ...
  // 첫 이미지가 들어오면 대표 이미지로 AI 태깅을 돌린다

const runAiTagging = async (file: File) => {
  setAiLoading(true);
  setAiResult(null);
  try {
    setAiResult(await productApi.aiTagging(file));
  } catch {
    setAiResult({ available: false, category: null, ... });
  } finally {
    setAiLoading(false);
  }
};
```

**사용자가 버튼을 누르지 않아도** 첫 이미지를 올리는 순간 자동으로 분석이 시작됩니다.

### 제안값 적용

```typescript
const applyAi = () => {
  if (!aiResult?.available) return;

  if (aiResult.color) setColor(aiResult.color);

  // "아우터 > 데님 자켓" 형태를 실제 카테고리 ID로 맞춰본다
  if (aiResult.category && categories) {
    const [mainName, subName] = aiResult.category.split(">").map((s) => s.trim());
    const parent = categories.find((c) => c.name === mainName);
    if (parent) {
      setParentId(parent.id);
      const child = parent.children.find((c) => c.name === subName);
      setCategoryId(child ? child.id : parent.id);
    }
  }
};
```

AI는 **문자열**("아우터 > 데님 자켓")을 주는데 우리는 **ID**가 필요합니다. 이름으로 찾아서 매칭하고, 못 찾으면 대분류로 떨어뜨립니다.

**"적용하기" 버튼을 눌러야 반영됩니다.** 자동으로 채우지 않는 게 중요합니다 — AI가 틀렸을 때 판매자가 모르고 등록하면 안 되니까요. AI는 **제안**이고 결정은 사람이 합니다.

## 13. 프론트 데이터 흐름 정리

```
사용자 클릭
   │
   ▼
페이지 컴포넌트
   │  productApi.getDetail(id)
   ▼
api/index.ts (도메인별 함수)
   │  http.get<ProductDetail>("/products/1042")
   ▼
api/client.ts (공통 처리)
   │  ① 토큰 헤더 추가

   │  ③ 204 / 에러 / 봉투 처리
   ▼
백엔드
   │  { success: true, data: {...} }
   ▼
api/client.ts → payload.data 반환
   ▼
useAsync → { data, loading, error }
   ▼
화면 렌더링
```

## 스스로 확인해보기

**Q1.** 페이지마다 `fetch`를 직접 쓰지 않고 `client.ts`로 모은 이유를 3가지 이상 말해 보세요.

**Q2.** FormData를 보낼 때 `Content-Type` 헤더를 직접 넣으면 안 되는 이유는?

**Q3.** 낙관적 업데이트(optimistic update)가 무엇이고 왜 쓰나요?

**Q4.** `ProtectedRoute`가 있는데도 백엔드에서 권한 검사를 해야 하는 이유는?

**Q5.** `useAction`의 `if (running) return false;`가 막는 문제는 무엇인가요?

<details>
<summary>답 보기</summary>

**A1.** ① 서버 주소·토큰 헤더·에러 처리 코드가 21개 페이지에 중복되는 걸 막는다 ② 응답 봉투(`{success, data, error}`) 벗기는 로직을 한 곳에서 처리한다 ③ 응답 타입이 정해져 있어 자동완성과 컴파일 타임 검증이 된다 ④ API 경로가 바뀌어도 한 파일만 고치면 된다.

**A2.** multipart 요청은 각 파트를 구분하는 boundary 문자열이 Content-Type에 포함되어야 하는데, 이 값은 브라우저가 생성합니다. 직접 헤더를 지정하면 boundary가 빠져서 서버가 본문을 파싱하지 못합니다.

**A3.** 서버 응답을 기다리지 않고 화면부터 먼저 바꾸고, 실패하면 되돌리는 방식입니다. 사용자가 즉각적인 반응을 느끼게 해서 체감 속도를 높입니다.

**A4.** 프론트 가드는 브라우저 개발자 도구로 얼마든지 우회할 수 있습니다. 프론트는 UX(엉뚱한 화면 대신 로그인 페이지로 안내)를 위한 것이고, 실제 보안은 반드시 서버에서 이뤄져야 합니다.

**A5.** 사용자가 버튼을 빠르게 여러 번 누를 때 같은 요청이 중복 전송되는 문제입니다. 결제 버튼이라면 주문이 두 건 생길 수 있습니다.
