## 1. Git이 5,586줄을 "변경됨"으로 표시

### 증상

작업을 시작하자마자 `git status`를 보니 손대지도 않은 파일 64개가 전부 수정됨으로 나왔습니다.

```
64 files changed, 5586 insertions(+), 5586 deletions(-)
```

추가된 줄과 삭제된 줄이 **정확히 같은 숫자**입니다.

### 원인

**줄바꿈 문자(CRLF/LF) 차이**였습니다.

| OS | 줄바꿈 |
|---|---|
| Windows | `\r\n` (CRLF) |
| Mac/Linux | `\n` (LF) |

파일 하나를 Windows에서 만들고 다른 도구가 LF로 저장하면, 내용은 똑같은데 Git은 **모든 줄이 바뀐 것으로** 봅니다.

### 어떻게 확인했나

```bash
git diff --stat      # 5586줄 변경
git diff -w --stat   # 아무것도 없음  ← 공백/줄바꿈 무시하면 변경 0
```

`-w` 옵션은 공백 차이를 무시합니다. 이걸로 **"내용 변경은 0"** 임을 확정했습니다.

### 해결

```gitattributes
# .gitattributes
* text=auto eol=lf

*.bat        text eol=crlf
*.cmd        text eol=crlf
gradlew      text eol=lf

*.jar  binary
*.png  binary
```

`* text=auto eol=lf` — 저장소 안에서는 항상 LF로 저장합니다. 각자 작업 폴더에서는 OS에 맞게 변환되고요.

```bash
git add --renormalize .    # 기존 파일을 새 규칙으로 다시 정규화
git commit -m "chore: .gitattributes로 줄바꿈(LF) 정규화"
```

### 왜 이게 중요한가

이걸 안 고치고 계속했다면 **모든 커밋에 5,586줄의 가짜 변경이 섞입니다.**

- 코드 리뷰가 불가능 (진짜 바뀐 3줄을 5,586줄에서 찾아야 함)
- `git blame`이 무의미 (모든 줄의 마지막 수정자가 나)
- 충돌이 상시 발생

팀 프로젝트라면 **첫날 반드시** 해야 하는 설정입니다.

### 교훈

> **diff의 숫자가 이상하면 내용이 아니라 형식을 의심하라.** 추가·삭제 줄 수가 같으면 거의 확실히 줄바꿈이나 인코딩 문제입니다.

## 2. 취소한 상품을 다시 살 수 없음

### 증상

아직 안 터졌습니다. 주문 취소 기능을 만들면서 발견했습니다.

### 원인

DDL에 이런 제약이 있었습니다.

```sql
CREATE TABLE orders (
    ...
    UNIQUE KEY uk_orders_product (product_id),   -- 상품당 주문 1건
);
```

"단일 재고 상품이니 주문도 1건"이라는 논리는 맞아 보입니다. 그런데 취소 흐름과 충돌합니다.

```
1. 구매자 A가 상품 1042를 주문       → orders에 1건 (product_id=1042)
2. A가 취소                          → 주문은 CANCELLED, 상품은 다시 ON_SALE
3. 구매자 B가 같은 상품을 주문        → INSERT 시도
                                     → uk_orders_product 위반! 💥
```

**상품은 판매중으로 돌아왔는데 아무도 못 삽니다.**

### 왜 놓쳤나

제약을 만들 때 **"현재 시점"만** 생각했습니다. "한 상품에 유효한 주문은 하나뿐"은 맞지만, **취소된 주문도 테이블에 남는다**는 걸 고려하지 않았습니다.

이력이 남는 테이블에 유니크 제약을 걸 때 흔한 실수입니다.

### 해결

```java
// orders/entity/Order.java
@Table(
        name = "orders",
        // ⚠️ DDL에는 uk_orders_product(상품당 주문 1건) 유니크 제약이 있었으나 제거했다.
        //    주문 취소 시 상품이 ON_SALE로 복귀하므로 같은 상품에 두 번째 주문이 생길 수 있는데,
        //    유니크 제약이 있으면 그 재주문이 DB 레벨에서 막혀버린다.
        //    "동시에 두 명이 사는 것"은 Product.markPaid()의 ON_SALE 상태 검사로 막는다.
        indexes = {
                @Index(name = "idx_orders_product", columnList = "product_id"),
                ...
        }
)
```

유니크를 빼고 일반 인덱스로 바꿨습니다. 중복 구매 방지는 **애플리케이션의 상태 검사**가 담당합니다.

### 남은 한계

동시성 문제가 남습니다. 두 요청이 **정확히 같은 순간** 들어오면 둘 다 `ON_SALE` 검사를 통과할 수 있습니다. 완벽히 막으려면 낙관적 락(`@Version`)이나 비관적 락이 필요합니다.

### 교훈

> **제약을 걸 때는 "이 데이터의 전체 생애주기"를 그려보라.** 생성·수정·취소·삭제·재생성까지 시나리오를 돌려봐야 합니다. 특히 이력이 남는 테이블에 유니크 제약은 위험합니다.

## 3. 주문 생성이 아예 불가능

### 원인

DDL의 배송지 컬럼이 전부 NOT NULL이었습니다.

```sql
CREATE TABLE orders (
    ...
    receiver_name  VARCHAR(50)  NOT NULL,
    receiver_phone VARCHAR(20)  NOT NULL,
    zipcode        VARCHAR(10)  NOT NULL,
    address1       VARCHAR(255) NOT NULL,
);
```

그런데 API 명세의 흐름은 이렇습니다.

```
POST /orders                    ← 주문 생성 (배송지 정보 없음!)
PATCH /orders/{id}/shipping     ← 나중에 배송지 입력
```

**주문을 만드는 시점에 배송지가 없습니다.** NOT NULL이면 INSERT 자체가 실패합니다.

### 왜 놓쳤나

DDL은 "완성된 주문의 모습"을 그린 것이고, API 명세는 "주문이 만들어지는 과정"을 그린 것입니다. **둘을 따로 설계하면 이런 어긋남이 생깁니다.**

DDL을 볼 땐 "주문에는 배송지가 있어야지"가 자연스럽고, API를 볼 땐 "결제 먼저, 배송지는 나중"이 자연스럽습니다. 두 문서를 나란히 놓고 대조해야 보입니다.

### 해결

```sql
    -- ⚠️ NOT NULL이었으나 NULL 허용으로 변경함.
    --    거래 흐름상 POST /orders(주문 생성) 시점에는 배송지가 없고,
    --    이후 PATCH /orders/{id}/shipping에서 채워지기 때문에 NOT NULL이면 주문 생성 자체가 불가능하다.
    receiver_name  VARCHAR(50)  NULL,
    receiver_phone VARCHAR(20)  NULL,
    zipcode        VARCHAR(10)  NULL,
    address1       VARCHAR(255) NULL,
```

대신 **출고 시점에 검사**합니다.

```java
// orders/entity/Order.java
public void ship(String trackingNo) {
    requireStatus(Status.PAID, ErrorCode.ORDER_NOT_SHIPPABLE);
    // 배송지가 없으면 물건을 보낼 수가 없다
    if (this.receiverName == null || this.address1 == null) {
        throw new BusinessException(ErrorCode.SHIPPING_ADDRESS_REQUIRED);
    }
    ...
}
```

### 교훈

> **NOT NULL은 "이 값이 항상 있어야 한다"가 아니라 "이 행이 존재하는 모든 순간에 있어야 한다"는 뜻이다.** 값이 나중에 채워지는 컬럼은 NULL을 허용하고, 대신 **필요한 시점에 애플리케이션이 검사**해야 합니다.

## 4. 상품 삭제가 100% 실패

### 원인

상품을 등록하면 입고 건이 자동으로 생깁니다.

```java
// products/service/ProductService.java
Product saved = productRepository.save(product);
inboundRepository.save(Inbound.createFor(saved));   // 입고 대기 건
```

그런데 삭제할 때는 상품만 지웠습니다.

```java
productRepository.delete(product);
```

`inbounds.product_id`가 이 상품을 가리키고 있어서 **외래키 제약 위반**으로 실패합니다.

### 왜 JPA가 안 지워주나

`Product`에 `cascade = CascadeType.ALL`이 있는데도 안 됩니다. **cascade는 JPA가 아는 연관관계에만 적용되기 때문**입니다.

```java
// Product 엔티티에 있는 것
@OneToMany(mappedBy = "product", cascade = CascadeType.ALL, orphanRemoval = true)
private List<ProductImage> images;      // ✅ 이건 지워짐

// Product 엔티티에 없는 것
// Inbound, Wishlist, Report로 가는 필드가 없음  → ❌ JPA가 모름
```

DB에는 `ON DELETE CASCADE`를 걸 수 있지만, `ddl-auto: update`로 만든 테이블에는 그 옵션이 안 붙습니다.

### 어떻게 찾았나

스크립트로 **`product_id`를 참조하는 엔티티를 전부 뽑았습니다.**

```python
for f, src in files.items():
    if '.entity.' not in f: continue
    if re.search(r'JoinColumn\(name = "product_id"', src):
        print(" -", f)
```

```
- Inbound
- Order
- ProductImage
- Report
- Wishlist
```

**5개**가 나왔습니다. 이 중 `ProductImage`만 cascade로 처리되고 있었죠.

### 해결

```java
// products/service/ProductService.java
@Transactional
public void delete(Long userId, Long productId) {
    Product product = findOwnedProduct(userId, productId);

    if (!product.isEditable()) {
        throw new BusinessException(ErrorCode.PRODUCT_NOT_DELETABLE);
    }

    // 이 상품을 참조하는 다른 테이블의 행을 먼저 정리해야 한다.
    // Product 엔티티에는 이들로 가는 연관관계가 없어서 JPA가 알아서 못 지우고,
    // 그냥 두면 외래키 제약에 걸려 삭제가 통째로 실패한다.
    //
    // (주문/결제/정산은 PENDING_INBOUND 상품에는 존재할 수 없으므로 대상이 아니다)
    inboundRepository.findByProductId(productId).ifPresent(inboundRepository::delete);
    wishlistRepository.deleteByProductId(productId);
    // 신고는 기록을 남겨야 하므로 삭제하지 않고 참조만 끊는다
    reportRepository.findByProductId(productId).forEach(Report::detachProduct);

    productRepository.delete(product);
}
```

### 삭제냐 참조 끊기냐 — 판단이 갈린 지점

| 대상 | 처리 | 이유 |
|---|---|---|
| Inbound | 삭제 | 상품 없는 입고 기록은 의미 없음 |
| Wishlist | 삭제 | 없어진 상품을 찜하고 있을 이유 없음 |
| **Report** | **참조만 끊기** | **신고 기록은 남겨야 함** |

신고를 지우면 **"이 판매자가 반복적으로 신고당했다"는 이력이 사라집니다.** 악용될 수 있죠. 그래서 `product`를 null로 만들고 기록은 유지합니다.

```java
// reports/entity/Report.java
/**
 * 신고 대상 상품이 삭제될 때 참조만 끊는다.
 * 신고 기록 자체는 남겨야 한다 — 반복 신고자 추적이나 처리 이력 확인에 쓰이기 때문.
 */
public void detachProduct() {
    this.product = null;
}
```

### 교훈

> **JPA의 cascade는 "엔티티에 선언된 관계"에만 동작한다.** DB에 FK가 있어도 엔티티에 필드가 없으면 JPA는 모릅니다. 삭제 기능을 만들 땐 **"이 테이블을 참조하는 곳이 어디인가"** 를 DB 기준으로 전부 확인해야 합니다.
>
> 그리고 **"지울 것"과 "남길 것"** 을 구분하세요. 기술적으로 지울 수 있다고 지워도 되는 건 아닙니다.

## 5. 상품 등록이 구조적으로 불가능

### 원인

명세를 그대로 읽으면 이렇습니다.

```
POST /products
  body: { images: ["https://.../1.jpg"] }   ← URL 배열을 요구

POST /products/{productId}/images
  form: file=<binary>                        ← 이미 존재하는 상품을 요구
```

**등록하려면 URL이 필요한데, URL을 얻으려면 상품이 있어야 합니다.**

### 왜 이렇게 됐나

명세를 쓸 때 **S3 presigned URL 방식**을 암묵적으로 가정한 것 같습니다. 그 방식은 이렇습니다.

```
1. 프론트가 S3에 직접 파일 업로드 (백엔드 안 거침)
2. S3가 URL 반환
3. 그 URL로 상품 등록
```

이 경우 백엔드는 URL만 받으면 되니 명세가 말이 됩니다. 그런데 우리는 **로컬 디스크 저장** 방식이라 백엔드를 거쳐야 하고, 그 통로가 없었던 겁니다.

### 언제 발견했나

**프론트 연동을 하다가** 발견했습니다. `ProductCreatePage`를 만들면서 "파일을 어디로 보내지?"에서 막혔죠.

백엔드만 만들 때는 `test.http`에서 이미 있는 URL 문자열을 넣어 테스트했기 때문에 안 보였습니다.

### 해결

```java
// products/controller/ProductController.java
/**
 * 상품 등록 전 이미지 업로드 → URL 반환.
 * ⚠️ 명세서에 없는 추가 엔드포인트다. ...
 * ⚠️ 경로가 /products/{productId}보다 구체적이라 "images"가 productId로 해석되지 않는다.
 */
@PostMapping(value = "/images/upload", consumes = "multipart/form-data")
public ResponseEntity<ApiResponse<Map<String, String>>> uploadImage(@RequestPart("file") MultipartFile file) {
    return ResponseEntity.status(HttpStatus.CREATED)
            .body(ApiResponse.success(Map.of("url", productService.uploadImage(file))));
}
```

### 교훈

> **API 명세는 "화면이 실제로 어떻게 쓸지"를 시뮬레이션해야 완성된다.** 엔드포인트를 하나씩 보면 다 말이 되는데, 사용자 흐름을 따라가면 구멍이 보입니다.
>
> 발표에서 쓸 만한 이야기입니다: "명세를 프론트에 적용하는 과정에서 순환 의존을 발견하고 보완했다."

## 6. 관리자가 출고할 주문을 찾을 수 없음

### 원인

관리자 API 명세에 이런 게 있습니다.

```
POST /admin/orders/{orderId}/ship        출고 처리
POST /admin/orders/{orderId}/deliver     배송 완료
POST /admin/settlements/{settlementId}/complete   정산 완료
```

전부 **`{orderId}`를 이미 알고 있다고 가정**합니다. 그런데 **목록을 조회하는 API가 없습니다.**

관리자는 주문 번호를 어떻게 알까요? DB를 직접 열어봐야 하나요?

### 해결

두 개를 추가했습니다.

```java
// orders/controller/AdminOrderController.java
/**
 * 주문 목록 조회 (status: PAID / SHIPPED / DELIVERED / CONFIRMED / CANCELLED).
 * ⚠️ 명세서에 없는 추가 엔드포인트 — 관리자가 출고할 주문을 찾으려면 목록이 필요하다.
 */
@GetMapping
public ResponseEntity<ApiResponse<PageResponse<OrderResponses.AdminItem>>> getOrders(...)
```

### 그리고 하나 더 얹었습니다

```java
// orders/dto/OrderResponses.java
private AdminItem(Order o) {
    ...
    // 배송지가 없으면 출고할 수 없다 — 관리자가 미리 알 수 있게 내려준다
    this.shippingReady = o.getReceiverName() != null && o.getAddress1() != null;
}
```

프론트에서 이렇게 씁니다.

```typescript
{o.status === "PAID" && !o.shippingReady && (
```

## 7. 카테고리 필터가 항상 빈 결과 ⭐ 실제로 터진 버그

### 증상

지훈님이 발견했습니다.

> "전체로 했을 때는 등록된 상품이 잘 뜨는데 상의, 하의, 신발, 가방을 눌렀을 때는 아무 상품도 안 뜨는데 왜이러는거야?"

### 진단 과정

**단서 1**: "전체"는 되고 특정 카테고리만 안 된다 → 카테고리 필터 조건이 문제

**단서 2**: 아우터는 1건이 떴다 → 완전히 망가진 건 아님

**단서 3**: 시드 데이터를 보니

```
아우터                 ← 레더 라이더 자켓 (여기만 대분류에 직접)
 ├ 데님 자켓           ← 데님 트러커, 코듀로이 셔츠 자켓
 ├ 코트                ← 울 오버코트
 └ 패딩                ← 경량 패딩 베스트
상의                   ← (없음)
 ├ 니트                ← 캐시미어 니트
 ├ 셔츠                ← 옥스포드 셔츠
 └ 맨투맨              ← 플리스 후드집업
```

**상품은 소분류에 붙어 있는데 필터는 대분류로 거른다.** 아우터가 1건 뜬 이유도 설명됩니다 — 우연히 대분류에 직접 붙은 상품이 하나 있었던 거죠.

### 원인

```java
// ❌ 처음 버전
predicates.add(cb.equal(root.get("category").get("id"), cond.getCategoryId()));
```

`category_id = 2`(상의)인 상품이 하나도 없으니 항상 빈 결과입니다.

### 왜 놓쳤나

**두 가지 실수가 겹쳤습니다.**

1. **카테고리가 계층 구조인 걸 알면서도** 조회를 평면적으로 만들었습니다. 엔티티에는 `parent`/`children`을 제대로 만들어 놓고, 정작 검색에서는 그 구조를 안 썼습니다.
2. **"상품은 어느 레벨 카테고리에 붙는가"를 명확히 정하지 않았습니다.** 대분류에 붙을 수도, 소분류에 붙을 수도 있는 상태로 뒀습니다.

### 해결

```java
// products/repository/ProductSpecification.java
if (categoryIds != null && !categoryIds.isEmpty()) {
    // ⚠️ equal이 아니라 in을 쓴다.
    //    상품은 보통 소분류(예: '니트')에 붙는데 사용자는 대분류('상의')로 거른다.
    //    equal로 비교하면 '상의'를 눌렀을 때 '니트' 상품이 하나도 안 걸린다.
    predicates.add(root.get("category").get("id").in(categoryIds));
}
```

```java
// products/service/ProductService.java
private List<Long> resolveCategoryIds(Long categoryId) {
    if (categoryId == null) return List.of();

    Category category = categoryRepository.findById(categoryId)
            .orElseThrow(() -> new BusinessException(ErrorCode.CATEGORY_NOT_FOUND));

    List<Long> ids = new ArrayList<>();
    ids.add(category.getId());
    category.getChildren().forEach(child -> ids.add(child.getId()));
    return ids;
}
```

`GET /categories/{id}/products`에도 같은 문제가 있어서 함께 고쳤습니다.

### 지금 구조의 한계

카테고리가 **2단계(대-소)** 라고 가정했습니다. 3단계가 되면 손자 카테고리는 안 걸립니다. 재귀적으로 모으거나, DB에 계층 경로를 저장하는 방식(`path = "1/5/12"`)이 필요합니다.

### 교훈

> **계층 데이터를 평면적으로 조회하면 반드시 구멍이 생깁니다.** "부모를 선택하면 자식도 포함되는가?"를 설계 단계에서 명시하세요.
>
> 그리고 **테스트 데이터가 현실적이어야 버그가 드러납니다.** 만약 시드에서 모든 상품을 대분류에 붙였다면 이 버그는 발표 직전까지 숨어 있었을 겁니다.

## 8. 시드 SQL의 GROUP BY 오류 ⭐ 실제로 터진 버그

### 증상

IntelliJ가 빨간 줄로 경고했습니다.

```
열 created_at은(는) 집계되거나 GROUP BY 절에서 언급되어야 합니다
```

### 원인

제가 쓴 확인 쿼리입니다.

```sql
-- ❌
SELECT p.id, p.title, ..., COUNT(i.id) AS image_count
FROM products p
LEFT JOIN product_images i ON i.product_id = p.id
WHERE p.description LIKE '[SEED]%'
GROUP BY p.id
ORDER BY p.created_at DESC;   -- ⭐ GROUP BY에 없는 컬럼으로 정렬
```

MySQL 8의 `ONLY_FULL_GROUP_BY` 모드는 **GROUP BY에 없는 컬럼을 SELECT나 ORDER BY에서 쓰는 걸 금지**합니다.

왜 금지할까요? `GROUP BY p.id`로 묶으면 각 그룹에 여러 행이 들어갈 수 있는데, 그중 **어느 행의 `created_at`을 쓸지 정해지지 않기 때문**입니다.

### 해결

`GROUP BY` 자체를 없앴습니다.

```sql
-- ✅ 이미지 개수를 스칼라 서브쿼리로 센다
SELECT p.id, p.title, ...,
       (SELECT COUNT(*) FROM product_images i WHERE i.product_id = p.id) AS image_count
FROM products p
LEFT JOIN categories c ON c.id = p.category_id
WHERE p.description LIKE '[SEED]%'
ORDER BY p.created_at DESC;
```

JOIN + GROUP BY 대신 서브쿼리로 세면 행이 뻥튀기되지 않아서 GROUP BY가 필요 없습니다.

### 함께 나온 문제 — `열 'suspended' 해결 불가`

같은 화면에 이 에러도 있었습니다. 이건 SQL 문법 문제가 아니라 **DB에 컬럼이 없어서**였습니다.

제가 신고 도메인을 만들며 `Product`에 `suspended` 필드를 추가했는데, **그 이후 백엔드를 재시작하지 않아서** `ddl-auto: update`가 컬럼을 만들지 못한 상태였습니다.

```
엔티티에 필드 추가  →  (재시작 안 함)  →  DB에는 컬럼 없음
```

`ddl-auto: update`는 **애플리케이션이 뜰 때만** 스키마를 반영합니다.

### 교훈

> **`GROUP BY`를 쓸 때는 SELECT와 ORDER BY에 등장하는 모든 비집계 컬럼이 GROUP BY에 있어야 합니다.** 개수만 세는 거라면 스칼라 서브쿼리가 더 간단합니다.
>
> **`ddl-auto: update`는 재시작 시점에만 반영됩니다.** 엔티티를 바꿨으면 서버를 한 번 띄우고, IntelliJ Database 탭도 새로고침(Ctrl+F5)해야 IDE가 새 스키마를 인식합니다.

## 마지막으로 — 이걸 발표에서 어떻게 쓸까

교수님이나 심사위원이 가장 좋아하는 답변은 **"완벽합니다"가 아니라 "여기까지 알고 있고, 이렇게 판단했습니다"** 입니다.

이런 식으로 말할 수 있습니다.

> "API 명세와 DDL을 각각 작성했는데, 구현 과정에서 **다섯 군데가 어긋나 있는 걸 발견**했습니다. 대표적으로 주문 테이블의 배송지 컬럼이 NOT NULL이었는데, 실제 흐름은 결제 후에 배송지를 입력하는 구조라 주문 생성 자체가 불가능했습니다. NULL을 허용하고 대신 출고 시점에 애플리케이션이 검사하도록 바꿨습니다."

> "카테고리 필터가 동작하지 않는 문제가 있었는데, 상품은 소분류에 등록되는데 필터는 대분류로 조회하고 있었습니다. 계층 구조를 조회에 반영하지 않은 게 원인이었고, 선택한 카테고리와 하위 카테고리를 함께 IN 조건으로 넘기도록 수정했습니다."

> "동시에 두 명이 같은 상품을 주문하는 경합 상황은 아직 완전히 막지 못했습니다. 현재는 상품 상태 검사로 대부분 걸러지지만, 완전히 해결하려면 낙관적 락(@Version)이 필요하다고 판단하고 있습니다."

**한계를 먼저 말하는 사람이 신뢰를 얻습니다.**
