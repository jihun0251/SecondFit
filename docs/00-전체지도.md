# 00. 전체 지도 — 오늘 만든 것이 어떻게 맞물려 있나

> 이 문서를 먼저 읽으세요. 나머지 문서는 여기서 언급한 조각들을 하나씩 파고듭니다.

---

## 1. 서버가 3개다

```
┌─────────────┐      ┌──────────────┐      ┌──────────┐
│  frontend   │─────▶│   backend    │─────▶│  MySQL   │
│ React+Vite  │ HTTP │ Spring Boot  │ JDBC │ secondfit│
│  :5173      │◀─────│   :8080      │◀─────│  :3306   │
└─────────────┘      └──────┬───────┘      └──────────┘
                            │ HTTP (이미지 1장)
                            ▼
                     ┌──────────────┐
                     │  ai-server   │
                     │  FastAPI     │
                     │  :8000       │
                     └──────────────┘
```

각각 **독립된 프로세스**입니다. 셋 다 따로 실행해야 하고, 하나가 죽어도 나머지는 살아 있습니다.

이게 중요한 이유: AI 서버가 죽어도 상품 등록은 되어야 합니다. 그래서 백엔드는 AI 서버 호출이 실패하면 `available: false`를 대신 돌려주고 넘어갑니다. 이걸 **fail-safe**라고 합니다. 만약 세 개가 한 덩어리였다면 AI 부분이 터질 때 전체가 같이 죽었겠죠.

## 2. 백엔드 패키지 구조 — 왜 이렇게 나눴나

```
com.example.backend
├── auth/            인증 (로그인, JWT)
├── users/           회원
├── categories/      카테고리
├── products/        상품
├── inbounds/        입고
├── orders/          주문
├── payments/        결제
├── settlements/     정산
├── reviews/         리뷰
├── wishlists/       찜
├── reports/         신고
└── global/          공통 (설정, 예외, 응답 포맷, 파일 저장)
```

패키지를 나누는 방식은 크게 두 가지입니다.

**(A) 계층별 (layer-first)**
```
controller/  ← 모든 도메인의 컨트롤러가 여기 다 모임
service/
repository/
entity/
```

**(B) 도메인별 (package-by-feature)** ← 우리가 쓴 방식
```
products/
  ├── controller/
  ├── service/
  ├── repository/
  ├── entity/
  └── dto/
orders/
  ├── controller/
  ...
```

(A)는 처음엔 깔끔해 보이지만 도메인이 10개가 넘어가면 `controller` 폴더에 파일 30개가 쌓입니다. "상품 관련 코드"를 고치려면 4개 폴더를 왔다갔다 해야 하고요.

(B)는 **같이 바뀌는 것들이 같이 모여 있습니다.** 상품 기능을 고칠 일이 생기면 `products/` 폴더만 열면 됩니다. 나중에 "주문 기능만 떼어서 별도 서비스로 만들자"가 되어도 폴더째 들어내면 됩니다.

> 💡 **왜 `global`은 따로 있나?**
> `ApiResponse`, `ErrorCode`, `SecurityConfig` 같은 건 특정 도메인 것이 아니라 전부가 씁니다. 이런 걸 도메인 폴더 안에 두면 "왜 상품 패키지 안에 로그인 설정이 있지?"가 됩니다.

## 3. 백엔드 5계층 — 요청 한 건이 지나가는 길

상품 상세 조회(`GET /api/v1/products/1042`)를 예로 따라가 봅시다.

```
① 브라우저
   ↓ HTTP 요청
② Spring Security 필터 체인   ← 토큰 검사, 접근 권한 확인
   ↓
③ ProductController           ← URL을 자바 메서드로 연결, 파라미터 꺼내기
   ↓ productService.getDetail(1042)
④ ProductService              ← 비즈니스 규칙 (조회수 +1, 없으면 404)
   ↓ productRepository.findById(1042)
⑤ ProductRepository           ← SQL 실행
   ↓ JPA/Hibernate가 SELECT 생성
⑥ MySQL
   ↑ 결과 행(row)
⑤ Repository → Product 엔티티 객체로 변환
   ↑
④ Service → ProductDetailResponse (DTO)로 변환
   ↑
③ Controller → ApiResponse로 감싸서 반환
   ↑ Jackson이 JSON으로 직렬화
① 브라우저가 JSON 수신
```

각 계층이 **한 가지 책임만** 갖습니다.

| 계층 | 하는 일 | 하지 말아야 할 일 |
|---|---|---|
| Controller | HTTP를 다룬다 (URL, 상태코드, 파라미터) | 비즈니스 로직 |
| Service | 비즈니스 규칙, 트랜잭션 경계 | HTTP를 아는 것 (`HttpServletRequest` 등) |
| Repository | DB 접근 | 비즈니스 판단 |
| Entity | 자기 데이터의 규칙을 지킨다 | 다른 도메인을 직접 호출 |
| DTO | 바깥에 보여줄 모양 | 로직 |

> 💡 **왜 이렇게 나누나?**
> "판매자만 상품을 수정할 수 있다"는 규칙이 Controller에 있으면, 나중에 배치 프로그램이나 관리자 기능에서 같은 로직이 필요할 때 복사해야 합니다. Service에 있으면 누가 부르든 규칙이 지켜집니다.

## 4. 실제 코드로 확인

우리가 쓴 상품 상세 조회 코드입니다. 위 그림과 대조해 보세요.

### ③ Controller — HTTP만 다룬다

```java
// products/controller/ProductController.java
@GetMapping("/{productId}")
public ResponseEntity<ApiResponse<ProductDetailResponse>> getDetail(@PathVariable Long productId) {
    return ResponseEntity.ok(ApiResponse.success(productService.getDetail(productId)));
}
```

- `@GetMapping("/{productId}")` : URL의 `{productId}` 자리 값을
- `@PathVariable Long productId` : 자바 변수로 받는다 (문자열 → Long 변환은 스프링이 해줌)
- `ResponseEntity.ok(...)` : HTTP 200으로 응답
- **비즈니스 로직이 한 줄도 없습니다.** 서비스에 넘기고 결과를 포장만 합니다.

### ④ Service — 비즈니스 규칙

```java
// products/service/ProductService.java
@Transactional
public ProductDetailResponse getDetail(Long productId) {
    Product product = productRepository.findById(productId)
            .orElseThrow(() -> new BusinessException(ErrorCode.PRODUCT_NOT_FOUND));

    product.increaseViewCount();   // 더티 체킹으로 UPDATE 됨 (save 호출 불필요)

    return ProductDetailResponse.from(product);
}
```

- 없으면 `PRODUCT_NOT_FOUND` 예외 → 나중에 404로 변환됨 (04번 문서에서 설명)
- 조회수를 올린다 → **`save()`를 안 부르는데 왜 저장되는지**는 03번 문서에서 설명
- 엔티티를 그대로 반환하지 않고 DTO로 변환 → 이유는 04번 문서

### ⑤ Repository — SQL

```java
// products/repository/ProductRepository.java
public interface ProductRepository extends JpaRepository<Product, Long>, JpaSpecificationExecutor<Product> {
}
```

**구현체가 없습니다.** 인터페이스만 있는데 `findById()`가 동작합니다. Spring Data JPA가 애플리케이션 시작할 때 구현 클래스를 자동으로 만들어 주기 때문입니다. 이 마법의 정체는 05번 문서에서 다룹니다.

## 5. 오늘 만든 것 요약

| 항목 | 수량 |
|---|---|
| 백엔드 클래스 | 88개 |
| API 엔드포인트 | 45개 (명세 42 + 필요해서 추가한 3) |
| 도메인 | 11개 |
| 프론트 페이지 연동 | 21개 |
| 발견·수정한 설계 결함 | 7건 |

### 거래 흐름 전체

이 프로젝트의 핵심입니다. 상태가 어떻게 흘러가는지 외워두면 코드가 훨씬 잘 읽힙니다.

```
[판매자]  상품 등록
            │  products.status = PENDING_INBOUND
            │  inbounds 레코드 자동 생성 (AWAITING)
            ▼
[관리자]  입고 확인
            │  inbounds.status  AWAITING → CONFIRMED
            │  products.status  PENDING_INBOUND → ON_SALE
            ▼
[구매자]  주문 생성 + 모의 결제
            │  orders 생성 (PAID)
            │  products.status  ON_SALE → PAID
            ▼
[구매자]  배송지 입력
            │  orders에 배송지 저장 (상태는 PAID 유지)
            ▼
[관리자]  출고 (송장 등록)
            │  orders.status    PAID → SHIPPED
            │  products.status  PAID → SHIPPED
            ▼
[관리자]  배송 완료
            │  orders.status    SHIPPED → DELIVERED
            │  products.status  SHIPPED → DELIVERED
            ▼
[구매자]  거래 확정
            │  orders.status    DELIVERED → CONFIRMED
            │  products.status  DELIVERED → SETTLED
            │  settlements 생성 (PENDING, 수수료 10% 차감)
            ▼
[관리자]  정산 완료
               settlements.status  PENDING → COMPLETED
```

**Product와 Order의 상태가 나란히 움직이는 게 보이시나요?** 이 둘이 어긋나지 않게 만드는 방법이 03번 문서의 핵심입니다.

## 6. 이 문서들을 읽는 순서

```
00. 전체 지도            ← 지금 여기
01. 인증 (JWT)           ← 모든 API의 앞단. 이거 모르면 나머지가 안 읽힘
02. JPA 엔티티와 연관관계  ← 데이터 다루는 법
03. 트랜잭션과 상태머신    ← 02의 연장. 가장 중요한 설계 결정
04. 계층 구조·DTO·예외     ← 코드를 왜 이렇게 나눴나
05. 쿼리와 성능           ← Repository 깊이 파기
06. 프론트엔드 연동        ← 백엔드를 어떻게 갖다 쓰나
07. 버그 노트             ← 오늘 잡은 7건. 제일 배울 게 많음
```

**A1.** 같은 규칙이 다른 진입점(배치, 관리자 기능, 다른 API)에서 필요할 때 재사용할 수 없고, HTTP 없이는 테스트할 수 없기 때문입니다.
