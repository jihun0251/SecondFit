# 03. 트랜잭션과 상태머신

> 오늘 한 설계 결정 중 가장 중요한 것이 여기 있습니다. "상태 전이를 엔티티에 넣는다"는 판단이 왜 나왔는지, 그게 없었으면 뭐가 무너졌을지 이해하면 이 프로젝트의 뼈대가 보입니다.

---

## 1. 트랜잭션 — 전부 되거나, 전부 안 되거나

거래 확정을 예로 봅시다. 이때 세 가지가 동시에 일어나야 합니다.

```
① 주문 상태:  DELIVERED → CONFIRMED
② 상품 상태:  DELIVERED → SETTLED
③ 정산 레코드 생성 (PENDING, 108,000원)
```

만약 ①②는 성공했는데 ③에서 DB 연결이 끊겼다면?

**구매자는 거래를 확정했는데 판매자는 돈을 못 받습니다.** 데이터만 보면 정산 대상인지 알 방법도 없고요.

**트랜잭션**은 이걸 막습니다. "이 묶음은 전부 성공하거나, 전부 없던 일이 되거나 둘 중 하나"를 보장합니다.

```java
// orders/service/OrderService.java
@Transactional
public OrderResponses.Confirmed confirm(Long buyerId, Long orderId) {
    Order order = findOrder(orderId);
    requireBuyer(order, buyerId);

    order.confirm();                                                    // ①②
    Settlement settlement = settlementRepository.save(Settlement.createFor(order));   // ③

    return OrderResponses.Confirmed.of(order, settlement.getId());
}
```

`@Transactional` 하나로 끝입니다. 메서드가 정상 종료되면 **커밋**, 도중에 예외가 나면 **롤백**(전부 취소)됩니다.

### 동작 원리

```
메서드 시작
  → 스프링이 DB 트랜잭션 시작 (BEGIN)
  → 메서드 본문 실행
  → 정상 종료 → COMMIT
  → 예외 발생 → ROLLBACK
```

스프링은 **프록시**로 이걸 구현합니다. `@Transactional`이 붙은 빈을 주입받으면 실제로는 원본이 아니라 "트랜잭션 여닫는 코드로 감싼 대리 객체"가 주입됩니다.

> ⚠️ **그래서 생기는 함정**: 같은 클래스 안에서 `this.otherMethod()`로 호출하면 프록시를 거치지 않아서 `@Transactional`이 **안 먹습니다.** 다른 빈을 통해 호출해야 적용됩니다. 초심자가 자주 당하는 함정이니 기억해 두세요.

### `readOnly = true`

```java
@Service
@Transactional(readOnly = true)   // 클래스 전체 기본값
public class ProductService {

    @Transactional                // 이 메서드만 쓰기 가능하게 덮어씀
    public ProductCreateResponse create(...) { ... }

    public ProductDetailResponse getDetail(...) { ... }   // readOnly 상속
}
```

읽기 전용 트랜잭션은 두 가지 이점이 있습니다.

1. **성능**: 뒤에 설명할 "더티 체킹"을 위한 스냅샷을 안 만듭니다. 메모리를 아낍니다.
2. **안전**: 실수로 수정해도 반영되지 않습니다. "이 메서드는 조회만 한다"는 의도가 코드에 드러납니다.

우리는 **클래스에 `readOnly = true`를 걸어 기본을 읽기로 두고, 쓰는 메서드만 `@Transactional`로 덮어쓰는** 방식을 썼습니다. 실수로 어노테이션을 빠뜨려도 안전한 쪽으로 기울죠.

## 2. 영속성 컨텍스트와 더티 체킹 — `save()`가 없는데 저장되는 이유

이 코드를 보세요.

```java
@Transactional
public ProductDetailResponse getDetail(Long productId) {
    Product product = productRepository.findById(productId).orElseThrow(...);

    product.increaseViewCount();   // 조회수 +1

    return ProductDetailResponse.from(product);
}
```

**`productRepository.save(product)`가 없습니다.** 그런데 DB에 반영됩니다. 왜?

### 영속성 컨텍스트(Persistence Context)

JPA는 트랜잭션 안에서 조회한 엔티티를 **1차 캐시**에 보관합니다. 이 보관소를 영속성 컨텍스트라고 합니다.

```
① findById(1) 실행
   → DB에서 SELECT
   → 영속성 컨텍스트에 Product(id=1) 저장
   → 동시에 "처음 읽은 상태"의 복사본(스냅샷)도 저장

② product.increaseViewCount() 실행
   → 자바 객체의 viewCount만 12 → 13으로 바뀜
   → DB는 아직 그대로

③ 트랜잭션 커밋 시점
   → JPA가 현재 객체와 스냅샷을 비교
   → "어? viewCount가 다르네"
   → UPDATE products SET view_count = 13 WHERE id = 1  자동 실행
```

이 자동 감지를 **더티 체킹(dirty checking, 변경 감지)** 이라고 합니다. "dirty"는 "처음 읽은 상태와 달라진" 정도의 뜻입니다.

### 그래서 이런 코드가 가능합니다

```java
// products/service/ProductService.java
@Transactional
public ProductUpdateResponse update(Long userId, Long productId, ProductUpdateRequest request) {
    Product product = findOwnedProduct(userId, productId);
    ...
    product.update(category, request.getTitle(), ...);   // 값만 바꿈

    return ProductUpdateResponse.from(product);          // save() 없음
}
```

```java
// orders/service/OrderService.java
paymentRepository.findByOrderId(orderId).ifPresent(Payment::refund);
// 결제 상태를 REFUNDED로 바꾸기만 하면 커밋 때 UPDATE 됨
```

### 반대로 `save()`가 필요한 경우

**새로 만든 객체**는 영속성 컨텍스트가 모릅니다. 그래서 `save()`로 등록해 줘야 합니다.

```java
Product product = Product.builder()...build();   // 아직 JPA가 모르는 객체
Product saved = productRepository.save(product);  // ⭐ 이제 관리 대상이 됨
```

정리하면:
- **새 객체 → `save()` 필요**
- **조회한 객체를 수정 → `save()` 불필요** (더티 체킹)

## 3. 상태머신 — 오늘의 핵심 설계

### 문제 상황

이 프로젝트에는 상태가 두 개 있습니다.

```
Product:  PENDING_INBOUND → ON_SALE → PAID → SHIPPED → DELIVERED → SETTLED
Order:                                 PAID → SHIPPED → DELIVERED → CONFIRMED
                                        └→ CANCELLED
```

그리고 이 둘은 **항상 나란히 움직여야** 합니다.
- 주문이 SHIPPED면 상품도 SHIPPED
- 주문이 취소되면 상품은 다시 ON_SALE

만약 어긋나면? 주문은 취소됐는데 상품이 PAID로 남으면 **그 상품은 영원히 아무도 못 삽니다.** 목록에도 안 뜨고 판매자도 어쩌지 못하죠.

### 나쁜 방법 — 서비스에 흩뿌리기

```java
// ❌ 이렇게 만들었다면
@Transactional
public void cancel(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow(...);

    if (order.getStatus() != Order.Status.PAID) {
        throw new BusinessException(ErrorCode.ORDER_NOT_CANCELABLE);
    }
    order.setStatus(Order.Status.CANCELLED);

    Product product = order.getProduct();
    product.setStatus(Product.Status.ON_SALE);   // 상품도 같이... 기억해야 함
}
```

문제가 뭘까요?

1. **까먹기 쉽습니다.** 다른 개발자가 관리자용 강제 취소 기능을 만들면서 상품 상태 되돌리는 걸 빠뜨리면 끝입니다.
2. **검사가 중복됩니다.** 상품 상태가 정말 PAID인지도 확인해야 하는데, 그 검사를 또 써야 합니다.
3. **추적이 안 됩니다.** "상품 상태가 왜 SETTLED가 됐지?"를 조사하려면 `setStatus` 호출부를 전부 찾아다녀야 합니다.

### 우리가 쓴 방법 — 엔티티가 자기 상태를 지킨다

**Product 쪽**

```java
// products/entity/Product.java

/** 주문 생성(결제) → 판매 중단 */
public void markPaid() {
    requireStatus(Status.ON_SALE, ErrorCode.PRODUCT_NOT_ON_SALE);
    this.status = Status.PAID;
}

/** 주문 취소 → 다시 판매중으로 복귀 */
public void returnToSale() {
    requireStatus(Status.PAID, ErrorCode.ORDER_NOT_CANCELABLE);
    this.status = Status.ON_SALE;
}

private void requireStatus(Status expected, ErrorCode errorCode) {
    if (this.status != expected) {
        throw new BusinessException(errorCode);
    }
}
```

**Order 쪽 — 자기 상태를 바꾸면서 상품도 함께 바꾼다**

```java
// orders/entity/Order.java

/** 관리자 출고 처리 */
public void ship(String trackingNo) {
    requireStatus(Status.PAID, ErrorCode.ORDER_NOT_SHIPPABLE);
    if (this.receiverName == null || this.address1 == null) {
        throw new BusinessException(ErrorCode.SHIPPING_ADDRESS_REQUIRED);
    }
    this.status = Status.SHIPPED;
    this.trackingNo = trackingNo;
    this.shippedAt = LocalDateTime.now();
    this.product.markShipped();          // ⭐ 상품도 함께
}

/** 주문 취소 (출고 전까지만) */
public void cancel(String reason) {
    requireStatus(Status.PAID, ErrorCode.ORDER_NOT_CANCELABLE);
    this.status = Status.CANCELLED;
    this.cancelReason = reason;
    this.product.returnToSale();         // ⭐ 상품도 함께
}
```

그러면 서비스는 이렇게 단순해집니다.

```java
// orders/service/OrderService.java
@Transactional
public OrderResponses.Shipped ship(Long orderId, OrderRequests.Ship request) {
    Order order = findOrder(orderId);
    order.ship(request.getTrackingNo());        // 상태 전이는 엔티티가 알아서
    return OrderResponses.Shipped.from(order);
}
```

### 이 설계가 주는 것

**(1) 상태를 바꾸는 길이 하나뿐**

`Product.status`를 바꾸는 방법은 `markPaid()`, `markShipped()` 같은 메서드뿐입니다. setter가 없으니 다른 경로가 없습니다. "상품 상태가 왜 이렇게 됐지?"를 조사하려면 이 메서드들의 호출부만 보면 됩니다.

**(2) 두 상태가 구조적으로 맞물린다**

```java
Order.ship()  → 자기: PAID → SHIPPED
              → product.markShipped() 는 상품이 PAID일 때만 성공

만약 어떤 이유로 상품이 이미 SHIPPED였다면?
  → markShipped()에서 예외 → 트랜잭션 롤백
  → 주문 상태도 원래대로 (아무 일도 안 일어남)
```

**둘 중 하나라도 조건이 안 맞으면 아무것도 안 바뀝니다.** 어긋난 상태가 만들어질 수 없는 구조입니다.

**(3) 규칙이 코드로 문서화된다**

```java
public void confirm() {
    requireStatus(Status.DELIVERED, ErrorCode.ORDER_NOT_CONFIRMABLE);
    ...
}
```

이 한 줄이 "거래 확정은 배송 완료 상태에서만 가능하다"는 비즈니스 규칙을 그대로 표현합니다. 주석보다 정확합니다 — 주석은 낡을 수 있지만 이 코드는 실제로 강제하니까요.

### 이런 접근을 뭐라고 부르나

**도메인 주도 설계(DDD)** 에서 말하는 **풍부한 도메인 모델(Rich Domain Model)** 입니다.

반대말은 **빈약한 도메인 모델(Anemic Domain Model)** 로, 엔티티는 getter/setter만 있는 데이터 자루이고 모든 로직이 서비스에 있는 형태입니다. 흔하지만 안티패턴으로 분류됩니다 — 객체지향의 "데이터와 그 데이터를 다루는 행위를 함께 둔다"는 원칙을 어기니까요.

## 4. 생성 시점의 검증

주문 생성도 같은 패턴입니다.

```java
// orders/entity/Order.java
public static Order create(Product product, User buyer) {
    if (product.isOwnedBy(buyer.getId())) {
        throw new BusinessException(ErrorCode.SELF_PURCHASE_NOT_ALLOWED);
    }
    product.markPaid();   // ON_SALE이 아니면 여기서 예외
    return new Order(product, buyer);
}
```

`new Order(...)`가 아니라 **정적 팩토리 메서드** `Order.create(...)`를 씁니다.

- 본인 상품 구매 금지 검사
- 상품이 판매중인지 검사 (`markPaid()` 안에서)
- 이 둘을 통과해야만 객체가 만들어짐

**"잘못된 주문 객체는 애초에 존재할 수 없다"** 는 상태를 만든 겁니다.

### 가격 스냅샷

```java
private Order(Product product, User buyer) {
    this.product = product;
    this.buyer = buyer;
    this.orderPrice = product.getPrice();   // ⭐ 값을 복사
    this.status = Status.PAID;
    this.paidAt = LocalDateTime.now();
}
```

`orderPrice`를 왜 따로 저장할까요? `order.getProduct().getPrice()`로 언제든 볼 수 있는데.

**판매자가 나중에 가격을 바꿀 수 있기 때문입니다.** 89,000원에 산 주문이 있는데 판매자가 가격을 50,000원으로 수정하면, 참조만 하고 있었다면 과거 주문 금액이 50,000원으로 바뀌어 버립니다. 정산액도 틀어지고요.

**거래 시점의 값은 복사해서 박제해야 합니다.** 이걸 스냅샷이라고 하고, 주문·결제·정산처럼 돈이 오가는 곳에서는 필수입니다.

## 5. 정산 — 파생 데이터도 생성 시점에 고정

```java
// settlements/entity/Settlement.java
public static final double FEE_RATE = 0.10;

private Settlement(Order order, User seller) {
    this.order = order;
    this.seller = seller;
    this.grossAmount = order.getOrderPrice();
    this.feeAmount = (int) (order.getOrderPrice() * FEE_RATE);
    this.netAmount = this.grossAmount - this.feeAmount;
    this.status = Status.PENDING;
}
```

수수료와 실지급액도 **계산해서 저장**합니다. 조회할 때마다 계산하지 않고요.

**왜?** 나중에 수수료율을 10% → 15%로 올리면, 계산 방식이면 **과거 정산 내역까지 전부 바뀝니다.** 이미 송금한 건의 금액이 달라지면 회계가 무너집니다.

> 💡 `(int)` 캐스팅은 소수점을 **버립니다**. 89,000 × 0.1 = 8,900.0이라 딱 떨어지지만, 89,999원이면 8,999.9 → 8,999원이 됩니다. 수수료를 덜 떼는 쪽(판매자에게 유리)으로 기울인 선택입니다. 반올림하면 1원을 더 떼게 되죠.

## 6. 별개의 축은 별개로 — `suspended` 이야기

신고 처리로 상품을 노출 중지시켜야 했습니다. 상태에 `SUSPENDED`를 추가하면 될까요?

```java
// ❌ 이렇게 했다면
enum Status { PENDING_INBOUND, ON_SALE, SUSPENDED, PAID, SHIPPED, DELIVERED, SETTLED }
```

**전이 규칙이 전부 오염됩니다.**

```java
public void markPaid() {
    requireStatus(Status.ON_SALE, ...);   // SUSPENDED에서 오면? 정지 해제하면 어디로 돌아가지?
}
```

"정지 전 상태"를 따로 기억해야 하고, 모든 전이에 "그런데 정지 상태라면?" 조건이 붙습니다.

**우리가 쓴 방법 — 축을 분리**

```java
// products/entity/Product.java
/**
 * 신고 처리로 노출 중지된 상품.
 * 거래 상태(status)와는 별개 축으로 둔다 — 상태머신에 SUSPENDED를 끼워 넣으면
 * 모든 전이 규칙이 "그런데 정지 상태라면?"으로 오염되기 때문.
 */
@Column(nullable = false)
private boolean suspended = false;
```

거래 상태는 그대로 두고, **노출 여부라는 독립적인 축**을 하나 더 만들었습니다. 목록 조회에서만 걸러내면 됩니다.

```java
// products/repository/ProductSpecification.java
predicates.add(cb.equal(root.get("status"), Product.Status.ON_SALE));
predicates.add(cb.isFalse(root.get("suspended")));   // 정지된 건 제외
```

> 📌 **일반화된 교훈**: 서로 독립적으로 변하는 것을 하나의 enum에 우겨넣으면 조합 폭발이 일어납니다. "이건 정말 같은 축의 값인가, 아니면 별개 축인가?"를 항상 물어보세요.

## 7. 트랜잭션 경계 안에서만 유효한 것들

```java
@Transactional
public ProductImageUploadResponse addImage(Long userId, Long productId,
                                           MultipartFile file, boolean isThumbnail) {
    ...
    ProductImage image = ProductImage.builder()...build();
    product.addImage(image);

    // flush를 해야 INSERT가 실행되어 image.id가 채워진다 (응답에 imageId가 필요)
    productRepository.flush();

    return ProductImageUploadResponse.from(image);
}
```

### `flush()`가 왜 필요한가

JPA는 **커밋 직전까지 SQL을 모아뒀다가 한 번에 보냅니다**(쓰기 지연). 그래서 `product.addImage(image)`를 해도 아직 INSERT가 안 나갔고, `image.getId()`는 **null**입니다.

`flush()`는 "지금 당장 모아둔 SQL을 보내라"는 명령입니다. INSERT가 실행되면 DB가 AUTO_INCREMENT로 만든 ID를 JPA가 받아서 객체에 채워 넣습니다.

응답에 `imageId`를 담아야 하니 여기서는 flush가 필요했습니다.

> 💡 `flush()`는 커밋이 아닙니다. SQL만 보낼 뿐 트랜잭션은 아직 열려 있어서, 뒤에서 예외가 나면 롤백됩니다.

## 8. 전체 흐름 다시 보기 — 거래 확정 한 번에 벌어지는 일

```java
@Transactional                                    // ── BEGIN
public OrderResponses.Confirmed confirm(Long buyerId, Long orderId) {

    Order order = findOrder(orderId);             // SELECT orders
    requireBuyer(order, buyerId);                 // 본인 주문인가? 아니면 403

    order.confirm();
    //   ├ requireStatus(DELIVERED)  ← 아니면 409, 여기서 롤백
    //   ├ this.status = CONFIRMED
    //   ├ this.confirmedAt = now()
    //   └ product.markSettled()
    //       ├ requireStatus(DELIVERED)  ← 아니면 409, 여기서 롤백
    //       └ product.status = SETTLED

    Settlement settlement = settlementRepository.save(Settlement.createFor(order));
    //   ├ grossAmount = order.orderPrice
    //   ├ feeAmount   = gross × 10%
    //   ├ netAmount   = gross - fee
    //   └ status      = PENDING

    return OrderResponses.Confirmed.of(order, settlement.getId());
}                                                 // ── COMMIT
//   더티 체킹으로 UPDATE orders, UPDATE products 자동 실행
//   + INSERT settlements
```

**어디서든 예외가 나면 세 개 전부 없던 일이 됩니다.**

**A1.** JPA의 영속성 컨텍스트가 조회 시점의 스냅샷을 갖고 있다가, 트랜잭션 커밋 시점에 현재 객체와 비교해서 달라진 필드에 대해 UPDATE를 자동 생성하기 때문입니다(더티 체킹).

**A2.** ① 상태를 바꾸는 경로가 하나로 모여 추적이 쉬워진다 ② Product와 Order 상태를 함께 바꾸는 걸 빠뜨릴 수 없다 ③ 전이 조건 검사가 한 곳에 있어 중복되지 않는다 ④ 조건이 안 맞으면 예외가 나서 트랜잭션이 롤백되므로 어긋난 상태가 저장될 수 없다.

**A3.** 판매자가 나중에 가격을 수정하면 과거 주문의 결제 금액까지 바뀌어 버리기 때문입니다. 거래 시점의 금액은 복사해서 고정해야 정산·회계가 어긋나지 않습니다.

**A4.** 노출 중지는 거래 진행 상태와 **독립적인 축**이기 때문입니다. 같은 enum에 넣으면 모든 전이 규칙에 "정지 상태라면?" 예외 처리가 붙고, 정지 해제 시 원래 상태로 돌아갈 방법을 따로 기억해야 합니다.

**A5.** 기본값이 안전한 쪽(읽기 전용)이라 어노테이션을 빠뜨려도 실수로 데이터가 변경되지 않습니다. 또 읽기 전용은 더티 체킹용 스냅샷을 만들지 않아 메모리·성능 이점이 있습니다.
